### 443 的坑（重要）
- 443 的 Caddyfile 是 **`/home/ubuntu/futureme/deploy/portal/Caddyfile`**（bind mount `:ro`），
  **不是** `/opt/yihot/deploy/Caddyfile`（那个 218 字节，md5 都不同，是参考件）。
- Caddy 的 `header` 指令**不带 `>` 前缀 = 追加**，不是覆盖。应用再设一遍就变成
  `x-content-type-options: nosniff` × 2。浏览器对 nosniff 是**整串比较**，`"nosniff, nosniff"` 不等于
  `"nosniff"` → 等于把规则废掉，比不加还糟。
- 解法：应用按 `X-Forwarded-Proto === "https"` 分路——TLS 边缘来的交给 Caddy，直连 80 的由应用补，
  取值与 Caddy **逐字对齐**（`Referrer-Policy: no-referrer`、`Permissions-Policy` 不含 geolocation）。
  实测 80 与 443 各一份、逐字一致。
- 将来若想让应用当唯一来源：在那份 Caddyfile 的 `header` 字段前加 `?`（仅当不存在时才设），
  然后就能无条件设置。但不能随手重启 futureme-https（持 IP 证书、兜底反代 80，还服务 FutureMe）。

- 滑动窗口日志（`Map<key, number[]>`），键 = `ip|scope`；键上限 20,000，超了按插入顺序淘汰 1/4。
- 超限回 `application/problem+json`（`code=rate_limited`）+ `Retry-After` / `RateLimit-Reset`；
  成功响应也带 `RateLimit-Limit` / `RateLimit-Remaining`（头名被规范化成 `Ratelimit-*`）。
- **内网来源直接跳过**（`isPrivateAddress(req.ip)`）：页面 SSR 一次渲染连打两三个接口，计入访客额度
  等于让「刷新」消耗配额。实测服务器内网打 250 次全 200（额度 180），页面照常。

### 真正的坑：`TRUST_PROXY=false` 让 443 全站共用一个身份
- 之前 web 完全忽略 `X-Forwarded-For`，一律用 `req.socket.remoteAddress`。而 443 走
  Caddy（**host 网络**）→ `127.0.0.1:80` → docker-proxy → web，源地址是**容器网关**。
- 后果不止限流记成一锅：留言 5 次/分、登录 10 次/15 分**也是全站共用一个桶**，任何人都能把别人的
  额度用光（自己锁自己+锁所有人）。这是个一直存在、没人发现的 bug。
- 修法：`TRUST_PROXY=true` + **只在 TCP 对端本身是内网时才采信 XFF 最后一跳**，其余用源地址。
  Caddy 把真实地址追加在末尾 → 伪造的前缀无效；公网直连 80 时该头被整个忽略。
- `.env` 已改（备份 `.env.bak.20261116-0159`），`.env.example` 默认值也改成 true（有了硬约束，
  「反代 + 源站端口也对外」也不会被伪造绕过）。
- **实测**：80 与 443 同桶；伪造 `X-Forwarded-For: 1.2.3.4 / 10.0.0.1 / 127.0.0.1 / 172.17.0.1`
  打 443 与 80 **全部仍 429**。
