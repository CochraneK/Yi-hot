## 1. P0：需要纠正的恢复与安全风险

### G-01｜加密备份是否落后生产配置，尚未闭环

- **证据**：[2026-10-28 删除本地前审计](memory/2026-10-28.md)记载：生产配置有多项当时未纳入加密备份；已在本地明文归档补齐，仍需再加密。GitHub `secrets/credentials.env.enc` 最近可见提交为 **2026-10-09**，未见 10-28 后重加密的 Git 更新。
- **不能推断**：这不意味着生产密钥丢失、服务当前不能运行；只是 Git 中的备份**不能视为已验证可恢复的最新版本**。
- **建议动作**：由持有生产权限的维护者在**私有安全环境**只核对配置键名/版本与备份完整性（不得打印值），验证可恢复与口令保管，再决定是否改用专门秘密管理器或独立私有备份。**不要为解决这个问题把明文/新增加密密钥直接推到公开仓库**。现有公开 `.enc` 的长期存放策略和口令强度也值得复核。
- **验收**：有脱敏的「生产配置 ↔ 安全备份」键名覆盖统计、实际解密演练与最新备份日期；没有任何密钥值进入 commit/日志/PR。

### G-02｜GitHub main 与腾讯云生产的同一性仍需现场收据

- **证据**：当前 README 与 [PROJECT_CONTEXT](PROJECT_CONTEXT.md)反复说明，GitHub 提交不等于腾讯云已上传、重建、迁移或启用。此次只读 GitHub，没有服务器权限。
- **建议动作**：由有部署权限者使用现有 [三方同步工具](../tools/README.md)，输出**脱敏**的代码版本、配置模型名、数据库信源源数/启用/入选、主要容器状态、关键任务失败数和日期。不要自动执行数据库变更。
- **验收**：一份带具体检查时间和版本 SHA 的生产快照；与 GitHub 的差异清单已审阅。避免复活旧本地代码覆盖新 Git。

### G-03｜仓库已经 Public，但部分接手指南仍在使用 private 旧语义

- **证据**：2026-10-30 GitHub 仓库信息显示当前 `CochraneK/Yi-hot` 是上游 `KKKKhazix/AIHOT` 的 **public fork**；旧 `CochraneK/yi-hot-old` 已归档。README 和 [AIHOT_UPSTREAM_REBUILD §10-30](AIHOT_UPSTREAM_REBUILD.md)较新；[PROJECT_CONTEXT](PROJECT_CONTEXT.md)、[memory/MEMORY.md](memory/MEMORY.md)、[secrets/README](../secrets/README.md)仍含“private 仓库”等历史操作口径。
- **建议动作**：给关键旧文档加顶部「2026-10-30 覆盖说明」，**不擦除历史证据**；记录 canonical repo、旧仓只读、fork ancestry、Pages/Actions 是否实际启用及新增迁移需要注意的权限。记忆镜像是自动生成的，应更新源后重跑镜像工具，不应手改生成文件。
- **验收**：新人从 README/HANDOFF/PROJECT_CONTEXT 进入，不会按已废弃的私有仓库/旧迁移策略操作。

## 2. P1：资料已存在，但尚缺“截至今天”的统一真值

### G-04｜缺少跨 10-24→10-30 的最新一页运营交接

- **证据**：10-24 聊天归档完整；10-28 有安全备份专项日志；10-29 的省钱实验证据写在 [COST](COST.md)；10-30 的 fork、历史迁移、上游 token 处理写在 [AIHOT_UPSTREAM_REBUILD](AIHOT_UPSTREAM_REBUILD.md)，公众号停服与生态调研在 README / [RELATED_PROJECTS](RELATED_PROJECTS.md)。
- **问题**：内容**不一定丢失，但高度分散**。下一位 AI 若只读 10-24 的“下一步”会重复已做的工作；例如 10-29 优化已经完成，10-30 fork 已迁移，而早期文件还写着旧成本/旧仓状态。
- **建议动作**：以本审计为目录，另维护一页短 `CURRENT_STATUS`，只写当前版本、已完成、真正阻塞、最新实测日期，详细证据继续留在专题文档。状态字段必须区分 `planned / coded / tested locally / deployed / verified in production`。
- **验收**：每个 P0 事项只有一个明确权威位置和日期；已完成且证伪的优化建议不会重新开工。

### G-05｜跨仓公益实体主数据的落地证据仍需单独整理

- **用户已确定目标**：以 YiHot 作为唯一公益情报发布产品，逐步吸收 NewsMail 与 charity-intelligence 的可用资产；不为简化合并而破坏数据/证据链。
- **已实现部分**：邮件订阅与采集已分别有实现/部署文档；信源候选及事件采集覆盖也已大幅推进；单纯按旧整合路线的“SMTP 未实现”判断会误判。
- **仍需验收**：公益组织历史 SQLite/结构化资料是否仍可访问、备份与原始证据是否完整；`legacy_id → canonical_org_id` 映射、机构更名/同名问题及证据索引如何只读接入。当前已有[监管记录](REGULATORY_RECORDS.md)，**不等同** charity-intelligence 历史实体数据库已完整合并。
- **建议动作**：增加一张具体资产迁移表，按“旧项目模块/数据量基线/安全备份/目标模型/迁移状态/验证结果”逐项登记。历史 14,327 家是旧库某期说明，不应当作目前线上主库已有数量。

### G-06｜信源状态与预算口径的旧/新结论并存

- **证据**：10-23 的旧聊天快照记载 190 行 DB；10-25 [SOURCE_REGISTRY](SOURCE_REGISTRY.md)记载 210 源、175 启用、累计 1,868 入选；这是两个时点，均不能冒充 10-30 实时数。10-24 [QUEUE](QUEUE_SUSTAINABILITY.md)依赖旧五调用成本基线；10-29 [COST](COST.md)已实测结构抽取惰性、评分灰区、预筛首尾与缓存命中等优化，并推翻若干旧假设。
- **建议动作**：后续报告/信息图/费用月化自动标 **取数日期、数据层级、同一时间窗与分母**，按当前源类型（正式 seed、线上 DB、已启用、实际入池、特定机构）分别计数。代码是否部署需另验。
- **验收**：任何“一共多少源、一天多少钱、月化多少钱”都可以回溯到同一口径的导出/查询，不混用 10-23 的 190、10-25 的 210 及 10-30 的代码状态。

### G-07｜DeepSeek 生产实际路由仍需新回执

- **证据**：[模型切换方案](DEEPSEEK_FLASH_SWITCH_2026-10-21.md)和 [10-24 对话归档](HANDOFF-2026-10-24-CHAT-ARCHIVE.md)已保留用户关于 `deepseek-flash` 非思考模式、旧数据不重算的决定，但均提示后台/分阶段覆盖可能优先于默认模型、服务器改动未凭 Git 获证。
- **建议动作**：只读对账当前模型名（不是 key）、后台 `settings.models`、各阶段重定向与近期 `receipt_attempts`。不用为验证而重跑历史文章。
- **验收**：一篇新样本对应实际模型名、计费单位和人民币可复算；若已达标直接关闭此项。

## 3. P2：仍待产品化/交付，而不该误写成“聊天丢了”

### G-08｜“六张专题信息图”尚未形成完整交付集合

- **用户意图**：易读、精确的中国公益信源分层、地理覆盖、机构渠道、精选质量、成本/队列、未完成风险，不希望只有一张总图。
- **已有**：README 展示 SVG hero、flow、topics，[10-23 源图](assets/yihot-source-atlas-2026-10-23.svg)亦已归档。
- **缺**：10-24 聊天交接中提议的多张**同一数据口径、可核对与更新**的专题图并未全部见到；它们仍是**视觉交付待办**，并非架构数据没保存。
- **要求**：先用当期可复算数据制图，再交给图像工具做美学渲染；不得用旧 16/60、42 源快照当今天的数据。

### G-09｜X / 播客等多渠道愿景尚需明确“做、不做、延后”

- **来源**：早期讨论曾希望公众号、RSS、X、播客都能作为内容发现渠道。现行 README 明确 RSS、网站、搜索、邮件，公众号与微博暂停；现有文档里未发现一份对**播客内容进入此公益产品**的正式验收与否决表。
- **建议动作**：写短渠道决策矩阵（对用户价值、成本、合规、可持续性、当前状态），先定需求是否仍保留，再决定是否建 connector；不要因为口头提过就启用新爬虫。
- **验收**：每一类入口有 `active / paused / candidate / rejected` 状态、原因和验证门槛；无需为“完整”强行补全所有媒介。

### G-10｜AIHOT 同步成功 ≠ 功能 100% 对齐

- **证据**：10-30 真 fork、上游 ancestry graft 和 `vendor/aihot-main` 同步已有记录；它们证明 Git **能跟踪上游历史**，不等于现用 `main` 已自动拥有每项上游新功能。
- **建议动作**：维护一个只列实际差异的功能对齐矩阵（上游 SHA、模块、YiHot 保留的公益定制、是否适合、冲突/回归、部署结果）；不以一次 merge 的成功率代替产品能力验收。
- **验收**：能明确回答“继承了哪些、故意不做哪些、在哪些领域仍落后”，避免重写整套 AIHOT。

## 4. 不应为“完整”而进入公开 Git 的材料

- 生产明文 `.env`、管理员口令、GitHub/模型/邮件 Token、SSH 秘密、数据库 dump、订阅者邮箱及捐赠/个人资料明细；
- 受版权保护或未经授权的公众号全文、付费数据集、他人的私有仓库资产；
- 私人会议全文和无公开授权的人员画像；
- 机器特定的临时缓存、日志和未脱敏命令输出。

这类内容缺席**不是遗漏**；应该有私有备份与可恢复性验收，而不是纳入 public fork。
