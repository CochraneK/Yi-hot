## 06:35–07:05 llm 日预算锁死 8 小时 35 分钟（我昨晚埋的）

告警「Budget for llm exhausted (day)（661）」，站点 21:05 起停止更新。

**根因**：`checkBudget()` 的日窗口是**滚动 24 小时**（`receipt_attempts.service='llm' AND origin='live' AND started_at > now() - interval '1 day'`），不是自然日。11-16 的历史地点回填吃掉约 8,400 次（落在 16:00 / 17:00 / 20:00 北京三个桶），我 21:05 把 `per_day` 从 24,000 改回 9,000 时窗口里已经躺着 **9,039**——上限被改到当前用量之下，从那一秒起每个请求都被拒，而且只能等记录满 24 小时滚出窗口才可能解封。`BudgetExceededError` 的 `retryAfterSeconds=3600`，`afterFailure()` 把文章退回 `processing_state='new'` + `processing_retry_at=now()+1h`，于是每小时试一次、每次都被拒。

**处置**：`per_day` → **15,000**（note 写明 22:00 还原）；736 篇 `processing_retry_at` 直接置 `now()`，不等那一小时。sweep 每 5 分钟一次，`take` 在非高峰是 500。

**教训**：降 `per_day` 之前必须读一眼窗口用量。一个晚上的批量活儿能顶掉第二天的正常分析，这是滚动窗口的固有代价。

**留下来的定时任务**：`d6643d81`（一次性，11-17 22:15）——先查窗口，<7500 才改回 9,000，否则保持 15,000 并报告。

**观察口径**：`pgboss.job` 里 `content.analyze` 全是 `completed` 并不代表没事干，等待中的文章在 `articles.processing_state='new'` 上等 sweep，看积压要看 `articles`。

**成本**：近 7 天 24,360 次调用 ¥45.17，均价 **¥0.001854/次**；9,000 次/天 ≈ ¥17。`per_day` 是防失控的闸，不是省钱手段。

## 07:25–07:40 点「区」时地图与 No.01 一起跳

**根因**：`{!hasPoints ? null : …}` 把地图容器 gate 在「此刻有点」上。切档后新档还没缓存 → `visible=[]` → 容器卸载 → `map.current=null` 且实例 `destroy()`；卡片高度从 ~430px 掉到 ~90px，`继续看 No.0x` 以下全部上移，数据回来再长回去。同时底图瓦片重载 = 闪。

**改法**：
- 新增 `solid` state（一旦有过点就永久为真），容器只 gate 在 `solid` 上；create effect 的依赖也从 `hasPoints` 换成 `solid`。
- 红绘 effect 加 `if (!visible.length && waitingFor !== null) return;`——等新档时**保留旧圆点**，不再先清空。
- `setFitView` 改为 `fitted` ref 控制，**只在实例第一次绘制时**调用。原来每次红绘都调，切窗口/切层级会把读者的缩放拉回全国，这与文件头「switching the window only replaces the circles」的设计说明是矛盾的。
- 脚注 `hasPoints && !failed` → `solid && !failed`，否则等待期间那一行消失，又是一次高度抖动。

**实测**（Puppeteer + 本机反代 8910）：点「区」后 45/45 采样都是**同一个 DOM 节点**（`dataset.probe` 还在），卡片高度 delta 0，`继续看` 的 top delta 0，零 4xx、零 pageerror。唯一的高度变化是 +18px——区县脚注多一行，一次性的，不是闪烁。
