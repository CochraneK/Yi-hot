## 18:14 落实防复发三措施（已闭环，用户下令「落实」）
- **①「加超时」的真相（方向修正）**：查代码发现 HTTP 层超时其实已齐全——`lib/http-fetch.ts` 默认
  `AbortSignal.timeout(20s)`、所有抓取 12–30s、`providers/llm.ts:209` 的 LLM 调用 `AbortSignal.timeout(120s)`。
  **真正缺超时的是数据库**：`db.ts` 用 postgres.js，只有 `connect_timeout:10`（建连超时），**没有查询级超时**，
  且 `idle_timeout` 只对空闲连接生效。**根因 = 15:44 网关重建伴随网络抖动，某条已建立的 db 连接变半开，
  在该连接上的查询永久 pending**（postgres.js 这个版本无 `query_timeout` 选项），worker 主循环整条卡死、无 error、
  容器显示 Up 是假象。→ 修法不是重复加 HTTP 超时，而是**缩短 TCP keepalive 判定**：宿主
  `sysctl net.ipv4.tcp_keepalive_intvl=10`/`tcp_keepalive_probes=3`（持久化 `/etc/sysctl.d/99-yihot-keepalive.conf`）
  + `db.ts` 加 `keep_alive:10`（`socket.setKeepAlive(true,10s)`=TCP_KEEPIDLE）与 `max_lifetime:600` 双保险。
  半开连接约 40s 被 OS 关闭，postgres.js 随即 reject 挂起查询，任务失败重试而非卡死。
  `db.ts` 已 scp 宿主 + `build api` + `up -d --no-deps --force-recreate api worker web` 生效（本地 commit `9b4fc91`）。
