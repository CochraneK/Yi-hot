# 队列可持续与成本护栏

> 本文记录 2026-10-24 的实测基线、容量缺口、已落地的闸门与监控口径。
> 所有数字都标了口径与时间窗；不同窗口的数字不要相加或互相月化。

## 一、基线（2026-10-24 09:15 北京时间，生产库实测）

| 指标 | 数值 | 口径 |
| --- | --- | --- |

把额度放大到 6000 次/小时、并且 10-24 凌晨一口气跑了 7,500 次调用（¥8.39）。按这个速度，一天 ¥10–15。

## 二、容量缺口（必须说清楚）

一天能分析多少篇由预算决定，不由机器决定：

```
每日可分析篇数 ≈ 每日预算 ÷ ¥0.0062
¥3/天  → 约 480 篇
¥6/天  → 约 970 篇
¥10/天 → 约 1,600 篇
```

而入稿是 **1,400–2,100 篇/天**（其中 70% 是搜索源带回的历史稿）。所以：

- 要把成本压到 **¥3/天**，就必须让 **约 2/3 的入稿不进入付费分析**；
- 想一篇不漏地全分析，成本就是 **¥10–14/天（¥300–420/月）**，这是入稿结构的直接结果，不是配置问题。

**没有「既不减量又省钱」的开关。** 数据支持这个结论：搜索源带来的稿子里，入选率按相关性分档几乎均匀
（rerankScore ≥0.8 是 34%、0.2–0.4 是 28%、<0.2 是 26%），不存在「砍掉尾巴就能无损减量」的尾巴；
把回看窗口从 7 天收到 3 天，会丢掉 47% 的稿和 **53% 的入选**（近 7 天：3–7 天前发布的稿贡献 588 篇入选）。

所以本次落地的是**闸门**，而不是「优化掉浪费」——闸门把成本封在预算内，代价是超出的部分归档（可恢复）。

## 三、已落地的机制

### 3.1 三道闸门（按顺序，全部在花钱之前）

| 闸门 | 触发条件 | 结果 |
| --- | --- | --- |
| 日上限 | 当日历史稿已分析 ≥ `HISTORY_DAILY_MAX`（默认 120），或全站参考线 `DAILY_ANALYZE_QUOTA`（480）已用完 | 归档，`archive_reason='quota'` |
| 积压背压 | 历史待处理 ≥ `HISTORY_BACKLOG_MAX`（600），或最老一篇已等 ≥ `HISTORY_MAX_WAIT_HOURS`（96） | 归档，`archive_reason='backlog'` |
| 最长等待 | 已等超过 96 小时的历史稿（清扫时批量处理，每次最多 40 篇） | 归档，`archive_reason='stale-wait'` |

**例外通道**：标题命中「政策 / 法规 / 司法 / 研究」词表（`capacity.ts` 的 `WORTH_HISTORY`）的历史稿
**永远放行**，不受三道闸门任何一道限制。这是「不能仅凭超过 48 小时就判定不值得处理」的落地——
《未成年人保护法》修订、最高法典型案例、儿童发展报告不会因为发布得早而被归档。

**当日新闻不受任何闸门限制。** 挡今日新闻等于漏新闻，这个代价不能省。

### 3.2 归档不是删除

`processing_state='archived'` 与 `skipped` 的区别：

- `skipped`：本来就不需要分析（非编辑型信源的讨论帖）
- `archived`：**需要分析但被容量挡下**，只可能由三道闸门产生

归档保留原文、正文、来源、发现时间、分类候选（`archive_reason` + `archived_at`），只是没花那 5 次调用。
放回队列：

```bash
node scripts/requeue-archived.ts            # 全部原因，最多 200 篇
node scripts/requeue-archived.ts quota 500  # 只放回配额挡下的
```

放回时跳过闸门（人已经明确说「这些要」），但对后续自动流水每日上限仍然有效。

### 3.3 搜索源隔天跑（`config.everyNDays`）

**为什么不是改 `interval_minutes`**：搜索的幂等窗口是北京「当天」，把 12 小时改成 24 小时仍然是每天一次请求、
一分钱不少。唯一真正省搜索费的是「少跑一天」。

`everyNDays: 2` = 按源 id 哈希固定摊到隔天。回看窗口**保持 7 天不变**，所以覆盖面不丢，只是
发现时间晚 ≤1 天；搜索 API 从 ¥2/天 降到 ¥1/天。

### 3.4 监控

```bash
node scripts/cost-report.ts 7        # 钱：按天/阶段/题材
node scripts/queue-report.ts 7       # 队列：进/出/积压/等待/清空时间
node scripts/search-query-report.ts 7 # 每条搜索词的请求、花费、带来多少入选
```

`queue-report` 的判据是**日终积压是否连续三天上升**，不是「有没有排队」。
核心公式：`待处理变化 = 新增 - 完成 - 归档`。

### 3.5 搜索词级归因（本次新建）

- 费用：`receipts.request->>'query'`，**历史数据就有**，可回溯；
- 文章：`article_discoveries.query`，2026-10-24 上线，之前的记 unknown，不插值；
- 同一 URL 被多条词命中时只归给**首次带来它的那条**，所以「入选数」逐条相加等于总数，不会重复计费。

## 四、四档预算对应的真实取舍

以 ¥0.0062/篇、搜索 API ¥1/天（隔天跑）计：

| 档位 | `HISTORY_DAILY_MAX` | 每日约 | 每月 | 历史稿被归档 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 极简 | 0 | ¥2.7 + ¥1 = ¥3.7 | 约 ¥110 | 几乎全部 | 只跟当日新闻，历史只放政策/司法 |
| **当前默认** | 120 | ¥3 + ¥1 = ¥4.0 | 约 ¥120 | 约 1,100 篇/天 | 历史每天 120 篇的配额，60 天回填完 7 天窗口 |
| 均衡 | 300 | ¥4.5 + ¥1 = ¥5.5 | 约 ¥165 | 约 900 篇/天 | 历史覆盖明显更全 |
| 全量 | 不限 | ¥10 + ¥2 = ¥12 | 约 ¥360 | 0 | 一篇不漏，超出预算目标 |

服务器 ¥8.25/月 另计。上面只算 AI 与搜索。

## 五、本次没有做的事（附理由）

1. **不跳过 `structure_article`**。它占 llm 花费 22%（¥7.23/7 天），但产出 `publications.category`、
   `tags` 和 `fact`，而站点有 `/all` 全量动态与分类筛选——未入选的稿也公开可见。跳过会让这些稿
   失去分类，属质量下降，不做。
2. **不把两次独立评分并成一次**。用户明确要求暂不做。
3. **不缩短 `lookbackDays`**。近 7 天数据显示 3–7 天前发布的稿贡献 588 篇入选（占 53%），
   收到 3 天等于砍掉一半入选。
4. **不减少每源 query 数**。等 `search-query-report` 积累 3–7 天数据后按「单篇入选成本」逐条判断，
   现在砍只是拍脑袋。已知的两个零产出源（`search-samr`、`search-data-stats`）合计只占 ¥0.04/天。

## 六、验证方式

- `tests/capacity.test.ts`：闸门顺序、例外通道、归档保留原文、最长等待、放回队列；
- `tests/offpeak-history.test.ts`：高峰只取当日新闻、低谷再取历史；

## 七、坑

- `admitHistory` 的放行计数是**进程内、跨快照累加**的：只在跨自然日（北京时间）时归零。
  早先的实现跟着一分钟一次的快照一起清零，等于把「每天 120 篇」放宽成「每分钟 120 篇」，
  上限形同虚设；`tests/capacity.test.ts` 里有一条跨快照刷新的回归盯着它。
  由此带来的两个已知边界：**worker 重启会重新计数**（不是硬配额），多实例部署时每个 worker
  各自计数（实际放行量是「上限 × 实例数」）。当前单 worker，无影响。
- 余量用库里的当日完成数算，历史自己的用量用内存计数，**两者不能相加**：同一篇放进队列时记一次，
  分析完成后再在 `analyzed` 里记一次，相加就会算两遍，历史额度会被提前掐死。
- 归档只在 `processing_state='new'` 上生效；已被队列持有的稿不会半路被归档。
- `requeueArchived` 用 `attemptTag='from-archive'` 绕过闸门。归档稿没有历史分析结果，所以不会重复付费。
