### 纠正：搜索成本与 interval 无关，只与 query 条数 × 跑的天数有关（同日两次问）

**`interval_minutes` 对搜索源不产生任何费用差异。** `search.ts` 的幂等键是
`window = bjDay()` + `since`，北京「当天」之内同一 query 只真请求一次；interval 设 360 还是 720
都只付一次钱。实测印证：8 query 的源近 3 天调用 8 次、10 query 的 20 次（=query 数×2 天），
`cost_basis` 无 cache 行、`free` 恒为 0。所以「720→1440 砍半」是**错的**（上一条已删），
要跨 window 才省钱 → 只有「每 N 天跑一次」这一个形式。

真正口径：**73 个启用搜索源，配置里共 544 条 query/天 → 满跑 ¥2.72/天**（¥0.005 固定价，
搜索不分高峰，10-23 15 点 239 次与凌晨同价 ¥0.005）。**实测过去 24h 537 次、73 个源全部跑到、
¥2.68**，与配置数吻合。所以「不加源」的稳态是 **¥3.2–3.5/天、约 ¥100/月**（搜索 ¥81 + 新稿 ¥15–24），
比先前估的 ¥2.5 高不少。

降本只有三条，按杠杆排序：
1. **隔天跑 / 每 3 天跑**：lookbackDays=7，隔天乃至三天一次**都不漏稿**，只是晚发现。
   隔天 ¥1.36、三天 ¥0.91。要实现得加 `everyNDays`（在 fetchSearch 开头按 `日序 % N` 轮转跳过），
   因为 `interval_minutes` 上限 1440、且调它本身无效。
2. **砍 query 条数**：线性省钱。近 3 天 0 产出的 `search-samr`、`search-data-stats` 可直接停；
   `search-gqt-bj`(0.13)、`search-guangongwei`(0.17) 砍词。
3. **直连源的权重自适应已经存在**（`collect.ts` 的 `adaptIntervals`，按 7 天日均 `1440/(perDay*3)`
   夹在 15–60 分钟），但直连抓取本身免费，它省的是队列不是钱，别在这上面找成本。

  没顶到 20，现在并没有在丢**。所以「调整后才会漏」的前提要换成：**隔天跑会把两天量堆进同一次，
  才会顶满开始丢**，因此隔天必须同时把 `lookbackDays` 收到 3–4 天。`lookbackDays` 必须 ≥ 间隔+1。
- **count 拉满不是免费的**：计费虽与 count 无关，但候选翻倍会把 prefilter 推高一倍
  （prefilter ¥0.0014/次），20→50 约 +¥3/天。要提 count 必须同时提 `minAuthority`。
- 搜索的漏斗：13899 原始命中 → 11795 去重候选 → 2621 新入库（19%）。重复的 78% 不进 LLM，
  不花钱；所以「砍 query」省的是请求费，不是分析费。
- `receipts.subject` 只到 source 级，**没有 per-query 产出数据**，因此「砍哪些词」目前只能靠人工判断。
  要做数据驱动砍词，得先在 `fetch_runs.detail` 里按 query 记命中数。

**突发快通道几乎为空**：全库只有 `web-mem-emergency-news`（应急管理部，60 分钟）在跑，
中国地震台网 / 气象局 / 消防救援局都没有；`wechat-red-cross-disaster-center`（红十字会备灾救灾中心）
与 `wechat-social-disaster-relief` 两个救灾源都是 `paused`。直连抓取免费、只花新稿分析费
（¥0.0065/篇），补 4 个源约 +¥0.15/天，比拉长搜索间隔更对症。

**加源窗口回落要看滚动窗口**：窗口里压着 13000+ 次时直接 `normal`(6000) 会卡死新稿到下午，
得等滚出（约 13 小时）或分批下调。

### 事故：告警「新内容卡住 12 小时」其实是三件事叠在一起（03:40–03:55）

告警原文：19 篇等 2 小时以上，`Budget for llm exhausted (hour)` 242 次、`(minute)` 82 次。

**先分清积压构成**：当时 343 篇 `processing_state='new'` 里 **266 篇是 `backfill=true`（首采补历史）、
只有 77 篇是当日新闻**。回填稿在高峰被 offpeak 闸门压着等几小时是设计行为，但**告警没排除 backfill**，
于是天天响 —— 这才是「已持续 12 小时」的来源，不是新稿真卡了 12 小时。

三个真因，按发现顺序：

1. **凌晨集中入库打爆小时额度**：10-24 03 时一次性入库 324 篇，每篇 5 次调用 = 1620 次，
   而 `per_hour` 只有 3000（同时还在跑其他阶段）。03 时用掉 2591，剩下不够。
2. **撞额度后的退避是固定的 600 秒**（`BudgetExceededError(service,'hour',600)`）：这期间
   **即使把额度提上去也不会提前跑**，因为 `processing_retry_at` 已经在未来。所以「改额度」和
   「恢复」之间隔着最长 10 分钟，我一度误判为「改额度没生效」。判据：`max(updated_at)` 停在
   某分钟不再变化 = 全都在等 retry，不是进程死了。
3. **worker 03:39 之后不再产生任何 job**（`pgboss.job` 里 `content.analyze` 断在 03:41，
   `cron.content.sweep` 断在 03:45），日志只有一行 `worker started`、无报错。
   `docker restart aihot-worker-1` 才恢复。这是**静默停摆**，比卡稿危险。

处理与结果：额度临时提到 `per_minute=900 / per_hour=6000`（note 写明临时）→ 重启 worker →
live 稿 77→8、回填稿 266→75，5 分钟 1152 次调用。**确认恢复的判据是「积压数在降 + 每分钟有调用」**，
不是「日志有输出」。

顺手修了两处（`operations/alerts.ts`）：
- `waiting` / `oldest` / `failed` 全部加 `NOT coalesce(backfill,false)`，回填积压改在 `detail` 里附带
  「另有 N 篇回填稿在排队」，既不误报也不丢信息。
- 新增 `ops.scheduler` 告警：`cron.content.sweep` 超过 15 分钟没有新实例就报「后台调度停了」，
  直接给出 `docker restart aihot-worker-1`。

**未做，留给下次**：`hour` 窗口的 600 秒退避应按「窗口里最早那次调用滚出的时间」算，
否则每小时白撞 6 次；搜索源 15 时有 30 个源集中到期，会正撞工作日高峰，应当错峰到夜间。

**部署坑（新）**：`up -d --no-deps api worker` 起来后 worker 打印 `worker started` 却**不消费任何 job**
（`pgboss.job` 里 `cron.sources.schedule` 停在 `created`、没有 `cron.content.sweep` 新实例）。
再执行一次 `docker restart aihot-worker-1` 才恢复消费。所以部署后**必须验证 job 在流动**
（`SELECT name, max(created_on) FROM pgboss.job WHERE name LIKE 'cron.%' GROUP BY 1`，
有 < 5 分钟的实例才算好），不能只看 `worker started` 那行日志。

## 回填成本真相 + 回填排进半价时段（2026-10-24）

### 「历史回填」不是「加源首采」

`articles.backfill` 有两个来源（`materials.ts` `decideTimeline`）：`first-import`（新源首采）与
`stale-on-discovery`（**发现时原文日期已比发现时间老 48 小时以上**，`STALE_ON_DISCOVERY_MS`）。
后者**与 `initialBackfillLimit` 完全无关**，搜索源 lookback 7 天必然大量触发，所以看
cost-report 的「补历史」列不能直接当成「加源的账」。

近 7 天实测：first-import 2465 篇、stale-on-discovery 1646 篇。

### 生产库 212 个源全部显式配置，没有默认 30 遗留

分布：搜索 12（73 个）、8（136 个）、6（3 个 UNICEF）。`initialBackfillLimit` 兜底已从 30 改成 8。
10-23 那批 `search-*` 首采**每源 29–30 篇**、配置却写 12，原因是**配置是 10-24 才批量 UPDATE 的**，
首采发生在配置之前、走的是默认 30。判断「配置是否生效」要看 fetch_runs 的 new_count，
不要看现在的 config 值（那是事后改的）。

### 降首采上限不值得

加 20 个源、首采 8 篇 = 160 篇 ≈ ¥0.64；降到 4 篇省 ¥0.32。**每次加源省三毛**，还会让新源首屏少一半。
所以「回填花太多」的正解不是砍条数，而是下面这条。

### 已落地：回填只在半价时段跑

- `content.ts` 新增 `holdsHistoryForOffPeak()`；`queueProcessing` 对 `r.historical` 在高峰直接 return null；
  `sweepUnprocessed` 在高峰的 SQL 里加 `NOT (backfill AND (published_at IS NULL OR discovered_at-published_at>48h))`。
  **sweep 那条过滤是关键**：它按 `discovered_at` 倒序，回填稿的 discovered_at 就是采集时刻（最新），
  不加过滤会把每个高峰名额都填成回填稿。人工重算（`attemptTag`）不受限。
- 实测依据：近 30 天回填 ¥31.67 里 ¥9.93（31%）在高峰 → 挪低谷后同样活 ¥4.97，**30 天省约 ¥5**。
- 连带：weekly `0 10 * * 1`→`0 6 * * 1`、monthly `30 10 1 * *`→`30 6 1 * *`、
  catch-up 每小时→`15 0-8,12,13,18-23 * * *`（`compose.ts` 里 weekDue/monthDue 的 10 点门槛同步改成 6）。
- 顺带修 `peakSlotsLeft` 计数**没有上界**（只写 `started_at >= 小时起点`，别的时段一并计入；
  当前小时恰好等价所以线上没暴露，但测试传过去时间就炸）。

**大头仍是搜索费 ¥80/月**（73 源 537 次/天 × ¥0.005），压它只能隔天跑（省一半、晚一天），本次未动。

## 「砍搜索源还是砍首采」的账本结论（2026-10-24）

**首采是事件，搜索源是常态**，这是两个不同性质的账，不能按 7 天总额比大小。

逐日实测（¥）：

|---|---|---|---|
| 10-18 | 0.06 | 0 | 0 |
| 10-19 | 0.16 | 0 | 0.08 |
| 10-20 | 1.29 | 0 | 2.77 |
| 10-21 | 1.71 | 0 | 1.04 |
| 10-22 | 0.41 | 0.19 | 1.22 |

- 近 7 天 llm ¥31.74 + 搜索 API ¥4.03 = ¥35.77；**首采 ¥15.13（48%）确实是最大单项**，
  所以「首采贵」的直觉不冤，但它只出现在加源当天（10-23 一天 1505 篇）。
- **首采的钱 73% 属于搜索源**：search first-import 1797 篇 ¥11.11（73 源 × 平均 24.6 篇），
  web_list 558 篇 ¥3.10、json 111 篇 ¥0.82、rss 13 篇 ¥0.10。砍首采绕一圈还是砍搜索。
- **搜索源还有一笔不受首采上限管辖的钱**：`stale-on-discovery`（发现时原文已超 48h）
  search 1106 篇 ¥6.72/7 天 + live 489 篇 ¥2.73。lookback 7 天必然带回老稿，只能靠
  搜索源本身（隔天/减词/收窗口）降，改 `initialBackfillLimit` 一点用没有。
- **稳态成本修正**：搜索 ≈ **¥4/天（API ¥2 + 分析 ¥2）= ¥120/月**，不是之前说的 ¥2.7/天；
  全站稳态 ≈ **¥120–130/月**（不含加源）。此前说的「¥250–350/月」是错的——把 10-23 的首采
  尖峰当成了月化基数，重复计了一次。

## 成本优化 v1.1 落地（队列可持续 + 搜索归因）

新增 `packages/backend/src/jobs/capacity.ts`：历史稿在**入队前**过三道闸门（日上限
`HISTORY_DAILY_MAX` 120、积压 `HISTORY_BACKLOG_MAX` 600、最长等待 96h），被拦的记
`processing_state='archived'` + `archive_reason`，保留 body_text；`requeueArchived` 可放回。
当日新闻不受任何限制。迁移 `0046` 加 archived 状态与 `article_discoveries.query`。

**坑 1（最贵的一个）：`up -d --no-deps api worker` 不会重建 web，web 一直跑旧镜像。**
今天发现 web 容器创建时间停在 10-23 21:57、镜像 ID 还是旧的 `fd0d504a180d`，容器内
`industry/changelog.json` 停在 `2026-10-23T21:55`——几天里所有更新日志、关于页改动
**从来没上线过**。凡改动落在 web 渲染路径（changelog / site.ts / dashboard / 提示词），
`up -d --no-deps api worker web` 三个都要带。验证方式：
`docker exec aihot-web-1 head -c 60 /app/industry/changelog.json`。
另：站点在 `/yihot/` 子路径，`/changelog` 会 301 到 `/yihot/changelog`；宿主端口是 **80** 不是 3000。

**坑 2：新增配置键必须同时改「读取端」和 `config-keys.ts` 白名单。**
校验是白名单制，不认识的键抛 `unsupported config`，**不是忽略**——等于整类源从改配置那一刻
起每次采集都失败。我给 72 个搜索源加了 `everyNDays`，漏了白名单，09:25 起这些源全红，

**坑 3：`admittedSinceSnapshot` 跟着 60 秒快照一起归零**，等于把「历史每天 120 篇」放宽成

归零；余量用库里当日完成数、历史自己的用量用内存计数，**两者不能相加**（同一篇会被算两次）。
回归在 `tests/capacity.test.ts`「survives a snapshot refresh」，旧代码 `[true,true,true,true]`。

集中爆发），per_day 500 会在上午就打满，之后 search 源全部报 `Budget ... exhausted (day)`

否则 `0,0,4` 会被判成「连续三天上升」。
