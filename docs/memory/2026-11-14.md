## 09:40 站点全站不可达（服务器用户态卡死，待控制台重启）
**现象**：用户报「打不开」。
**实测**：
- SSH `22`：TCP `Connection established`，但**收不到 SSH 横幅**（timeout during banner exchange），连续 3 次复现。
- `443`：TCP 连上，`openssl s_client` 停在 `Connecting to ...`，无 TLS 响应。
- `80`：本机超时；第三方云端代理 `api.allorigins.win` 也 408 → **不是本地网络/代理/VPN 问题**。
- ICMP 通（8ms）→ 机器在网络层活着，是用户态没响应。
- 域名无意义：站点是 `SITE_URL=http://49.233.72.222/yihot`，DNS 与本故障无关（我一度误判为域名解析，已排除）。
**判断**：典型「根分区写满 / OOM 抖动 / 云盘 I/O 卡死」，sshd 与 443 代理同时不响应。需要腾讯云控制台重启。
**坑**：本机 `https_proxy=127.0.0.1:12597`（WorkBuddy 沙箱代理）会把 curl 失败包装成 `502 upstream connect failed`，**不能据此判断站点状态**；`/dev/tcp` 测 80 也不可靠（百度:80 同样 FAIL）。

## 10:40 查明 11-13 整机卡死根因（内存吃穿）+ 三条修复

**时间线（北京）**：17:35–17:38 六个采集任务 `job timed out`（web-cdrf/web-jyb/web-ndcpa/web-caixin/web-tophub-news/search-found-han）→ 17:40 起 publications 零入库、采集与分析同时停摆 → 22:00:43 内核 `global_oom` 连发 10 次（chromium 被杀 3 次，journald 自身崩溃）→ 22:31 整机用户态卡死 → 11-14 09:53 重启 → 09:54 pg-boss 补跑热榜。

**根因**：2GB 内存被吃穿。worker 里跑共享 headless chromium（6 个 `render:"browser"` 源），峰值 1GB+；`api/worker/db/web` 四个容器 **mem_limit 全为 0**，内核做的是**全机 OOM**（按全局挑牺牲者），最后 sshd 也被饿死 → TCP 能连但无响应。`apport` 在 chromium 反复崩溃时被唤醒，进一步放大。

**第 4 个独立 bug（顺带发现）**：`deliver.ts` 里 `response = 'below today\'s top'` 裸写进 postgres.js 模板字符串，PG 视作 `'below today\'` + `s top'` → `syntax error at or near "s"`。而这张卡**其实已发送成功**（sent_at 有值、postWebhook 返回 ok），随后的记账 UPDATE 抛错被外层 catch 捕获，把刚发的 10 条改成 `unknown`。已参数化 + 移出 catch + 独立 try。恢复：`UPDATE ... SET status='sent' WHERE response LIKE 'PostgresError: syntax error%'` 改回 10 条。

**修复三件套**：
1. `docker-compose.yml` 加 `mem_limit`：db 640m / api 448m / worker 960m / web 192m → OOM 落在 memcg，只杀 chromium。
2. `systemctl disable --now apport` + 清 `/var/crash`。
3. `worker-watchdog.sh` 加判据二「采集静默」：`fetch_runs` 60 分钟为空即计一次（近 7 天正常最大间隔 15 分钟），连续 3 次重启；容器启动 40 分钟内不判。**旧判据要求 `new>0`，采集先死时 new 归零 → 全程沉默 5 小时**，这是这次没能自愈的关键。另把「容器已死」检查移到 DB 查询之前（DB 一起挂时 q() 返回空会提前 exit）。

**验证**：容器镜像统一 `c22621d`；`docker inspect` 四容器限值就位；参数化 SQL 探针 `SELECT ${"below today's top"}` → `param-ok`；`cron.notify.hot-daily = 30 20 * * *` 在册；站点 /yihot/hot 200。部署后 held 113 条，20:30 出今日卡。

**未解决**：内存总量仍 1.9GB，三条防护只是把「整机失联」降级为「单容器被杀 + 自动重启」；根治要 2核4GB。同机 futureme/anydoor/werss 还各占 100–500MB。

## 11:20–11:35 anydoor 补齐额度上限（抄 FreeLLMAPI 三层）

**起因**：用户问"网关不记录任何一家的额度，怎么知道总额度"，随后看了 FreeLLMAPI 源码（`server/src/services/ratelimit.ts`），用户说"抄"。

**FreeLLMAPI 的做法（源码实证）**：① `models` 表 4 列 rpm/rpd/tpm/tpd（人工按文档填，随 catalog 每日更新）；② provider 级硬编码默认表 + `PROVIDER_DAILY_REQUEST_CAP_*` env 覆盖，按 UTC 日界；③ `learnLimitFromError()` 从错误体正则抠 `limit N` + 轴关键词回写 DB，`WHERE col IS NULL OR col > ?` **只下调永不调高**；④ 滑动窗口 + 内存/SQLite 双写 + 在途租约；⑤ 429 阶梯冷却 2m→10m→1h→24h + Retry-After 下限。讽刺点：它自己把 OpenRouter 记成 1000/日，实际 50/日。

**落地到 anydoor（server.mjs 改 3 处约 150 行）**：
1. `providerFromFile` 读 `quota_rpm/quota_rpd/quota_tpm/quota_tpd`；`api.txt` 给 openrouter/openrouter-b 填 50/日、llm7 填 100000 token/日 + 60/min、kilo/kilo-b/zhipu 只写 `quota_note`（200 req/h、1 并发，无对应轴）。
2. 新增 `QuotaLimitsStore`（`data/quota-limits.json`，只下调）+ `effectiveQuotaLimits`（declared 与 learned 取 min）+ `parseQuotaLimit`（先认轴再认数，tpd→tpm→rpd→rpm）+ `learnQuotaLimitFromError`（在 `recordProviderUsage` 的 error 分支调用）。
3. `computeProviderQuota` 不再写死 `limit: null`；`routeChain` 把「日额度已耗尽」的 provider 挪到链尾（不删除）；修 OpenRouter probe：读 `data.usage`（原来读不存在的 `total_usage`）并优先返回 `free_model_daily_requests{used,limit}`。

**关键坑（两个）**：
- **容器里跑的是镜像内的 server.mjs，改宿主文件+restart 无效**（`docker exec grep` 计数 0）。已在 `docker-compose.portal.yml` **和** `docker-compose.yml` 的 gateway.volumes 加 `./gateway/server.mjs:/app/gateway/server.mjs:ro`，recreate 一次后生效；**以后改网关代码只需 `docker restart anydoor-gateway-1`**，不用 rebuild。
- **`normalizeConfig` 有一张 snake→camel 白名单**，`quota_rpd` 不在表里 → 热重载时被丢弃，面板仍显示 `-`。必须把 4 个字段加进白名单（这是第一版上线后 limit 仍为 null 的真正原因）。

**验证**：容器内 `node --check` + 6 组断言单测（解析/只下调/合并/耗尽/持久化）全过；admin 接口现在显示 `llm7 rpm 60 / tpd 100000`、`openrouter rpd 50`、`openrouter-b rpd 50`；重启后 40 条调用全部 kilo-b/zhipu 成功，**openrouter/openrouter-b/llm7 零尝试**（本地计数 533/375 早已超 50/50，被跳过），之前每分钟都在白撞 429。学习链路探针：`limit 25, tokens per minute` → tpm=25 落盘，再喂 900 被拒。

## 11:34–11:47 Kilo 额度是否该按小时匀速分配

**用户问**：Kilo 是每小时限额，是不是可以更好地分摊到每小时。

**结论：不该做匀速。** 额度是 60 分钟滚动窗口、**不可累积**，匀速不增加总量还压低峰值。用 10 分钟 300 次需求的算例：burst 下 Kilo 能接 200（67%），匀速 3.3/min 只接 33（11%），免费额度利用率掉 6 倍。

**证据**（audit.jsonl，按分钟统计）：
- 11-11T21：前 18 分钟 130 次成功 → 18–47 分连续 429 → **48 分突然恢复**（最早那批滑出窗口）。
- 11-14T02：00–05 分 227 次全成功 → 09–51 分 43 次尝试全 429 → 56 分起 94 次全成功。
- 前提修正：`200 req/hour per IP` 不是硬数。`kilo` 是 `auth=none`（按 IP 认），`kilo-b` 是 JWT 账号，两套独立；kilo-b 单自然小时最高 **297** 次成功，kilo 最高 146。

**顺手挖出的真问题（比 Kilo 严重得多）**：
1. **openrouter 与 openrouter-b 是同一账号**（`/auth/api/v1/auth/key` 返回相同 `creator_user_id` 与 `workspace_id`，两边都 `free_model_daily_requests {used:68, limit:50}`）→ 共享 50/日，第二个 key 不扩容。openrouter-b 3 天 **199 次调用 0 次成功**，11-14T02 一小时白撞 176 次 429。
2. 11-14T02 该小时 621 个 error 的构成：longcat 348（额度早已耗尽，配额改造后已停用）+ openrouter-b 176 + Kilo 双 key 仅 43（**7%**）+ 其余 48。
3. 日额度型（openrouter 50/日、llm7 100k token/日）在凌晨 01–02 点**一次打光**，之后全天零供给。

## 14:50–15:10 yihot 接入 Exa 搜索（第二条搜索引擎）

**用户诉求**：给 yihot 加 Exa 的「免费搜索额度」功能。

**为什么值得做**：deepseek-tools 是近 14 天第二大支出（¥17.5，仅次模型 ¥46.8）。Exa 新账号每月赠 $10（Lite $4/1000 次 ≈ 2,500 次/月，no card），免费额度内不花钱。

**已落地**：
- 新增 `packages/backend/src/providers/exa.ts`：`exaSearch()` 走 `paidRequest`（service=`exa`），`route: "egress"`；优先用响应 `costDollars.total` 记 `basis='actual'`，缺失才退 `service_prices('exa','')` = USD 0.004。
- `sources/search.ts`：加 `config.engine`（默认 deepseek）；Exa 分支用 `startPublishedDate` 参数，`splitDateMarkers()` 把 `after:/before:` 从 query 剥出转参数；Exa 的 `publishedDate` 是完整时间戳 → 不写 `publishedAtPrecision`（默认 datetime），不像 DeepSeek 要退日级。
- `sources/config-keys.ts`：search 白名单加 `engine/exaType/exaCategory/exaHighlights/minScore`；`VALUES` 里 `engine` 只认 deepseek|exa（拼错会被拒，不会静默退回继续花 DeepSeek 的钱）。
- `database/migrations/0049_exa_search.sql`：`budgets.exa = 6/20/60`（60/天 ≈ 1800/月 × $0.004 = $7.2，留 28% 给 contents）+ `service_prices('exa','')` USD 0.004。**已在生产库应用并核对**。
- `tests/exa-search.test.ts`：8 个纯函数测试全过；`npm run typecheck` 全量通过。

**三条不能踩的设计点**：
1. **默认不取 contents**。Exa 的 text / highlights / summary 各按 $1/1000 页额外计费；一次 10 条结果默认带 highlights，费用约为搜索本身 2.5 倍，免费额度会掉三倍速。`needContent`/`exaHighlights` 才开。
2. **`minScore` 独立**。Exa `score` 是 0–1，与 DeepSeek `rerank_score` 的 0–3 不是同一把尺子，复用 `minRerank` 会把好结果全丢掉。
3. **记账分开**。Exa 额度单位是美元信用，混进 `deepseek-tools` 会让「花了多少」和「还剩多少免费额度」两笔账串味，预算熔断也会互相误伤。

**连通性实测**：服务器无 `EGRESS_PROXY_URL`，但 `api.exa.ai` 直连可达（Cloudflare，connect 0.19s / TLS 0.39s）。无 key 返回 **402**（`X402_PAYMENT_REQUIRED`，Exa 新推的 x402 协议），不是 401 —— 我代码里 402 已归为不可重试，正确。
