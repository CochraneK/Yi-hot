# 2026-10-22

## 审计：AIHOT 用没用最新 DeepSeek API

**结论：模型是最新的，但两个东西没用上/坏了。**

### 模型：已是最新
- `LLM_MODEL=deepseek-flash` —— 官方当前规范名，对应 **DeepSeek-V4.1-Flash-1017**（10-17 那版）。
  不是弃用别名（`deepseek-chat` / `deepseek-reasoner` 将于 2026/07/24 弃用）。
- `/v1/models` 只返回两个：`deepseek-flash`（上下文 1M、输出 384K、支持图像）与 `deepseek-v4-pro`。
- 切换时间点：receipts 里 `deepseek-chat` 最后一条 **2026-10-21 14:56**，`deepseek-flash` 第一条 **15:12**。
- `settings` 表无 `models.*` 覆盖 → 全部能力共用默认模型，JSON Output 已开（`jsonMode=true`）。
- `LLM_EXTRA_JSON={"thinking":{"type":"disabled"}}`：关思考是刻意选择（结构化评分任务），
  未用新参数 `reasoning_effort`（flash 支持 low/high/max，默认 high）。**不开思考时无意义，开着只会更贵。**

### 没用的：10-17 新开放的 Search / Fetch API
无 `kind=search` 采集器，`providers/` 里只有 llm/everyinfra/jina/dailala/socialdata/embeddings。完全没接。

### 坏的：成本记账全部为空
- 近 7 天 **7471 次 LLM 调用，`cost` 全为 NULL**（`currency` 也为空）。
- 根因：`service_prices` 只有一条 `(service='llm', model='deepseek-chat', USD, 0.3/1.2, verified 2026-10-09)`，
  而 `priceFor()` 先用 `serviceOf(model)` 查 MODELS 注册表拿 service —— 注册表里现在叫 **`deepseek`**，
  model 名也变成 `deepseek-flash`。**service 和 model 两个维度同时对不上** → 返回 null → 从不计价。
  （`admin/models.ts` 的注释其实已经写明这个陷阱："a price row whose model is not in the registry is never used"。
  旧行 `deepseek-chat` 也不在注册表里，所以连旧模型时代也没计过价。）
- 单价本身也过期：USD、0.3/1.2 是 V3 时代价。官方现行（元/百万 tokens）：
  - 命中 0.02（空闲）/ 0.04（高峰）
  - 未命中 1 / 2
  - 输出 4 / 8
  - 高峰 = 周一至周五 9-12、14-18（不含法定节假日）
- **还有一个代码缺口**：`costOf()` 只用 `input_per_mtok`，**不读 `cached_per_mtok`**，
  usage 里明明有 `prompt_cache_hit_tokens`（近 21h 命中 2.79M / 未命中 1.61M，命中率 63%）。
  只补价格行的话会把全部输入按未命中价算，21h 会算成 ¥4.5（真实约 ¥2.0），高估一倍。

### 按官方单价实算（近 21h，1571 次调用）
4.4M 输入（2.79M 命中）+ 0.085M 输出 → **¥2.0（全空闲）~¥4.0（全高峰）**。
平稳日约 300 次调用 ≈ **¥0.5–0.8/天**。7 天合计约 ¥10–19（含 10-16 / 10-20 / 10-21 三个回填日）。

## 详情页钟点抓不到的真实原因（13:30 修）

**症状**：原文页明明印着「2026-10-22 08:42」，卡片却只标「原文发布日期」。

**三层原因，缺一层都拦住了**：
1. `collect.ts` 的 `need.date` 只在「列表没有日期 / 显式 upgradeDatePrecision / reposted」时为真
   → 列表给了日级的源，根本不读详情页。
2. 68 个启用的 web_list 源里只有 19 个配了 `detail`；40 多个 probe 源没有 detail 配置，
   `if (!d || detailUsed >= detailBudget) continue` 直接跳过。**这是主因**。
3. `fetchDetail` 的兜底 meta 选择器写死小写 `name="pubdate"`，而中国政府 CMS 印的是
   `name="PubDate"`——CSS 属性值选择器**大小写敏感**，静默 miss。

**修法**：
- `pagePublishedAt(html, expectDay, utcOffset)` 收敛成唯一兜底：遍历所有 meta 按 **lower 后比名字**
  （含 PubDate/PublishDate/publish_time/dc.date…）、`<time>`、JSON-LD、`时间：` 标签、裸 `YYYY-MM-DD HH:MM`、
  最后才裸日期。`expectDay` 是安全阀：候选必须落在列表已声明的那天。
- `collect.ts` 加独立额度 `dateUpgrade`：`c.publishedAtPrecision === "date"` 就允许读详情页，
  预算 `_aihot.dateUpgradeMaxFetches`（默认 6/源/轮），与 `detail.maxFetches` 分开记账。
- **判据必须是 `=== "date"`，不能是 `!== "datetime"`**：rss/json_list/x 三个采集器从不设
  `publishedAtPrecision`，用后者会把它们的准确时钟也当成日级去重抓一遍。
- search 源的 `date` 来自检索索引，常差一天（URL /20261022/ 却记 10-21），故不传 expectDay，
  替换窗口放宽到 2 天。

**结果**：80 条抽样 49 条（61%）能升级；全量回填 775 条修好 **563 条（73%）**，
`articles` 精度分布 datetime 861→**1432**、date 779→**212**。
福建民政厅 10-22 08:42 正是用户举的那种例子。

`fetch_runs.detail` 现在记 `dateUpgrades` / `detailPages` / `dateOnlyFound`，
以后「为什么还是只有日期」直接从跑批记录里看，不用再猜。

## 搜索源热度：按站点计参与者（13:22 修）

`participantKey` 原本只有 `source:<id>` / `group:<x>`。搜索源是一个源，所以
「同一件事被 5 家媒体报道」在 `story_signals` 里 GROUP BY 后只算 **1 个参与者**，
而热榜 `MIN_PARTICIPANTS = 2` → 搜索抓来的事件天然上不了榜，越热越显示不热。

改成 kind=search 时返回 `site:<siteHost>`（`mzt.hunan.gov.cn`→`hunan.gov.cn`）。

### 一、原文印着 08:50，卡片只标「收录」——握手就失败，不是解析

```
fetch failed  cause: ERR_SSL_BAD_ECPOINT   # Node 22/OpenSSL 3，ecdhCurve 默认 auto
```

服务器先提 X25519，对方回的曲线点 OpenSSL 判非法，TLS 直接崩。浏览器与本机 curl 曲线顺序不同，所以都正常。

改法（`lib/http-fetch.ts`）：握手报 `ERR_SSL_BAD_ECPOINT`/`EPROTO` 时，同一请求换只提供 P-256
的 Agent（`connect.ecdhCurve='prime256v1'`）重试一次；只对直连生效（代理端 TLS 不归我们管）。
验证 `200 datetime 2026-10-22T00:50:04Z`。同批被误判停用的源里，西藏民政厅、最高法、广西民政厅
