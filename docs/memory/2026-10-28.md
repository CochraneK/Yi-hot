## 周报会被搜索延迟"串周"吗（2026-10-28 实测，已经一次更正）
**更正：上一轮"周报按到达日归周、45% 漂移"的结论是错的**——那是拿了日报分支算的。
- 机制：`reports.weekly` cron 周一 06:00 生成上一自然周（`schedules.ts:50`，`addDays(now,-7)`）。
- **归周口径（正确）**：周报/月报走 `composePeriod` → `candidates(...,{selectedOnly:false, includeBackfill:true})`，按 `coalesce(published_at, timeline_at)` 即**原始发布日**归周、且含回填（`compose.ts:232-237`）。`visible_after`（到达日）分支只用于**日报**（`composeDaily` 默认 attribution='timeline'）。
- 后果：周一 06:00 生成时，发布在周末、但搜索要 2–3 天才索引到的稿还没到 → 周一那版缺周末。**W43 实测**：合格池 1709 篇；周一前到 1408 篇（去重 1049 entries，取 top 120）；**周一之后又到 301 篇（约 18%）没进周一那版**。
- **修法（用户选定②：周一生成、周三更新）**：周一照常生成；周三加一个 cron 强制重算上一周 `composeWeekly(label,"wednesday-refill")`（`saveReport` 会记 revision 并原地覆盖）。周三的 label 公式同周一：`isoWeekLabel(addDays(beijingDate(now),-7))`（周三 −7 仍落在上一周）。
- **成本**：重算一期 = **1 次 report 调用**（`composePeriod` 只发 1 个 chatJson，maxTokens 4000）；实测同一 subject 均价 **¥0.0048**、最贵 ¥0.0236 → **≈¥0.02/期、<¥0.1/月**。不含文章评分（评分是采集时正常发生，重算只重读已入库的合格池）。
- 注意：邮件若周一发（`send_reports.py --kind weekly`，宿主侧），订阅者拿到的仍是不完整版；要订阅者也拿完整版，需把发信挪到周三（另议）。

## freellm（聚合 API 平台，非本地模型）部署建议

- 落地：先用 `scripts/eval-selection.ts` 做 A/B（同批稿对比入池质量）影子跑一周再切，不要直接全量。
- 省钱优先级：降调用量（砍低产源/强化 ingestNoiseFilter）> 换便宜单模型 > 免费聚合轮换。

## 补充：月报同款刷新（2026-10-28 下午）
用户「月报也这样」，已落地为 `reports.monthly-refill | 20 6 1 * *`（1 号 06:20，早于原来 06:30 那条）。
- label 取**两个月前**：m<=2 → `y-1 / m+10`，否则 `y / m-2`（1 月刷上一年 11 月、2 月刷上一年 12 月）。即"刷新上个月 1 号发的那期"。
- 两处刷新统一走**新增的 `compose.ts: refillPeriod(kind,key)`**：先 `SELECT 1 FROM reports` 判断存在，缺的期次返回 `null` 交给 `catchUpReports`，**刷新绝不凭空建空期次**；reason 统一记 `period-refill`。已在容器内实测 `refillPeriod('monthly','2026-13')` → 返回 `null`（不写库、不调模型）。
