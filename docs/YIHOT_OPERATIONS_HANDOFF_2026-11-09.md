# 第一部分 · 认识并使用 YiHot

## 1. 执行摘要：它为什么存在

公益资讯不缺来源，但来源分散：政策、社会组织官网、基金会项目、国际组织研究、行业媒体、邮箱简报、网页搜索。一个人在不同网站来回刷新，既费时间，也容易漏掉跨领域的变化。YiHot 想把这件事从“人每天重复搜索”变为“系统持续采集、机器初步整理、人核验重要信息”。

它提供的不是“所有消息都可信”，而是三种可以组合的价值：

1. **发现**：在较广的公开来源中发现与儿童及公益行业有关的新内容。
2. **理解**：用中文标题、短摘要、主题标签、机构归属、事件归组降低阅读门槛。
3. **跟踪**：把同一事件的新进展、热门事件、周报和月报串成可追溯的线索。

**不应期待的能力**：完全无遗漏、100% 准确、所有站点都可抓、自动判断违法与否、自动代表机构表态、代替调查记者或科研人员独立验证。每张卡片应回到原始发布者核实事实。文章版权、机构标识和数据使用许可不因被 YiHot 收录而转移。

**适合的五类人**：儿童保护与项目同事、公益机构运营与筹资人员、公共政策与社会工作研究者、教育及健康领域观察者、希望系统化理解公益行业的普通读者。不同角色无需理解同一层技术细节。

## 2. 网站地图与最短阅读路径

**线上入口**：[YiHot 网站](https://49.233.72.222/yihot/)；**管理员入口**：[后台](https://49.233.72.222/yihot/admin)（需要独立授权的管理员凭据）。部分环境使用 IP 证书，浏览器可能给出安全警告：不能因此建议用户忽略证书风险，应由维护者核实证书部署及域名策略。

目前公开页面以“总报、动态、热点、主题、更多”为主：手机底部固定五个入口，电脑使用侧栏。首页 `/` 在精选首页关闭时会转向 `/all`；因此看到“全部动态”并不意味着精选评审能力消失。

| 入口 | 主要回答什么问题 | 用法与注意点 |
|---|---|---|
| `/all` · 动态 | 最近收集了哪些公益信息？ | 按原文发布日期分组；用“只看未读／只看精选”缩小范围；以卡片原文链接核验 |
| `/hot` · 热点 | 哪些事件最近受到多方关注？ | 按事件而非单篇文章聚合；热度是信号强弱而不是真伪或重要性的绝对排名 |

### 2.1 一位读者的 90 秒操作示范

打开首页 → 点“动态” → 查看最近两日 → 选择感兴趣的主题 → 读卡片标题和摘要 → 注意“原文发布”和“本站收录”时间是否不同 → 点击原始链接核验 → 必要时收藏或分享。若想系统了解前因后果，进入“事件”页面而非只读一篇。

### 2.2 一位公益项目负责人如何使用

每周先读周报，了解政策与行业变化；在主题页关注儿童保护、营养健康、教育及相关募资政策；重大合作、项目或舆论判断要回到政府公告、机构原文或更多独立来源交叉核实。YiHot 应被用作**早期线索和优先级提示**，而不是代替内部立项、合规、伦理或风险审查。

## 3. 四种典型工作流

**工作流 A｜政策观察**：选择儿童保护／网络保护／教育相关主题 → 找原始政府发布 → 核对发布日期、适用范围、生效日及修订状态 → 形成内部政策要点。引用政策时保留原文链接和发布机关，避免把媒体解释当法规原文。

**工作流 B｜同行动态**：关注救助儿童会、中国儿童少年基金会、乡村发展基金会、壹基金、国际儿童组织等 → 按机构与事件阅读 → 比较项目目标、地区、资金方式和合作形式。多渠道转载同一稿件不能算多家独立组织的立场。

**工作流 C｜儿童权益事件预警**：看热点与司法／儿童保护专题 → 区分“举报”“立案”“起诉”“判决”“回应”“救助”各节点 → 标记可证实与待证实 → 需要对外发声时以官方进展为准。对涉未成年人个案不扩散身份和不必要的敏感细节。

**工作流 D｜研究与报告**：从 YiHot 找候选论文、统计报告和机构发布 → 导出原始来源清单 → 核对原报告方法、样本、时间段和定义 → 独立分析。AI 摘要不构成科研证据；可用“文献发现—核实—引用—复现”链路代替“直接引用摘要”。

## 4. 主题体系：内容形式和议题不是一回事

YiHot 当前的儿童公益重点覆盖十二个核心领域：**儿童教育、营养健康、性别平等、儿童保护、网络保护、青年发展、亲子养育、残障融合、应急救援、环境保护、募集筹款、政策倡导**。2026-11-02 起“养老服务”具有独立前台入口；“其他领域”是兜底。故在当前前台可见 **12 个核心使命领域 + 养老服务 + 其他领域 = 14 个筛选项**。README 有时把包含养老服务的专题称为“13 个使命主题”，不应据此误读 14 个筛选入口为 14 个独立儿童使命领域。

同一内容可以同时属于儿童保护、网络保护和政策倡导；但不应再同时带“其他领域”。**议题主题、内容形式、机构主体、地理层级、来源等级、发布时间精度**应作为不同维度管理。举例：一份 UNICEF 儿童保护统计报告，“主题＝儿童保护／营养健康”，“形式＝研究报告”，“来源＝国际组织”，“层级＝全球”，“证据类型＝统计分析”，并不相互替代。

## 5. 如何理解精选、未读与热点

- “**未读**”是个人阅读状态，主要在浏览器保存；不是系统判断内容质量。
- “**精选**”是 YiHot 通过预筛、评分及规则得到的站内入选结果；不同源可能使用不同的阈值。**分数不是事实真伪概率，也不是机构公信力评级**。
- “**热点**”是近时段、独立参与者与时间衰减合成的关注度。系统要求足够的独立证据，不能只凭若干搜索信号独立上榜。热度高不代表正确、重要或应该转发。
- **读者应做的核验**：发布主体是谁；文章发布时间和事件发生时间是否一致；是否为转载；多个来源是否真的相互独立；有无更晚的更正、撤稿或判决进展。

## 6. 邮件订阅、分享与多端使用

访问 `/subscribe`，填写邮箱，收到确认邮件后主动确认，选择周报或月报。系统为每位订阅者独立发送邮件，不对其他收件人公开地址；用户可从邮件中的入口退订。此流程由站点产生订阅与投递 outbox，独立 SMTP 服务发送邮件；**接收新邮件与生成 AI 报告是不同进程**，订阅人数增加不会按人数重复运行 AI 生成周报。

移动端适合“打开—扫读—收藏—转发”；桌面适合“主题交叉—长文核验—后台操作”。分享卡片或海报应保留原文归属及链接。公共 API、RSS、MCP、Agent Skill 属于对外读取方式，并不意味着开放所有管理功能。

## 7. 发布日期、收录时间与历史稿

YiHot 强制区分三个问题：**什么时候发生／原文何时发布／本站何时收到**。原站只写“2026-11-01”时，不能臆造“11:23”；系统记录 `published_at_precision='date'`；有完整时刻则记录为 datetime。无日期才使用可辨别标注的收录时间。当前 `/all` 按原文发布日期分组，日内采用已有规则安排；这与 10 月 22 日曾经按收录日展示的旧版本相反，**11 月 2 日的改动推翻了旧规则**。

搜索源通常回看近 7 天，是为了补漏；回看的旧稿不能伪装成“今天刚发生”。初次接入某源还有历史回填，但有限制：搜索源通常最多 12 条，其他常见源 8 条，UNICEF 部分源 6 条，且受时间窗口和内容质量约束。**入库历史并不等于要推送历史消息**。

### 8.2 生产数据库快照（2026-10-25）

已导出的真实运行台账记录 **210 条、启用 175 条、停用 35 条**；按运行态来源类型为 **搜索 72、网页列表 93、RSS 26、JSON/API 17、外部系统 2**。累计入选文章 1,868 条：搜索 1,256（约 67%）、网页 465（25%）、RSS 80（4%）、JSON/API 52（3%）、外部系统 15（1%）。**这些数据是 10 月 25 日时点的观测值，不是 11 月最新实时计数。**

它同时证明了一个运营事实：**同样是“1 条信源”，搜索源与官网列表源的成本、结果丰富度、权威性、去重难度完全不同**。不能仅用“总数增了多少”评价系统进展。

### 8.3 来源等级与参与模式

`T1` / `T1.5` / `T2` 是内容筛选中的源等级或运营分档，并不等同于科学质量排名或政府机构级别。`first_party` 表示是否为一手来源，`participation_mode` 则影响某信号能否直接参与正式内容发布；例如搜索命中的个人观点应先作为“发现信号”，不能未经核实冒充机构正式发布。

## 9. 五层信源地图：从权威到现场

**2026-11-09 文档补充：** [信源接入与治理图谱](SOURCE_ATLAS.md) 展示 2026-10-25 的采集方式分布、实际入池贡献与三维治理逻辑。图中技术入口与下述五个业务层是不同维度，不能相互推算；尚未形成按 31 省/原始发布主体去重的覆盖缺口统计。

为了兼顾“广度、深度、权威与信息差”，建议用**五个正交业务层**给信源做阅读导航，而不是把它们强塞进一个长名单。

1. **政策与治理层**：中国政府网、民政部、教育部、两高、全国妇联、残联、省级民政厅。重点看法律法规、实施细则、政策解读、监管公示。
2. **国际组织与研究层**：UNICEF、WHO、UNESCO、世界银行、联合国新闻、Innocenti。重点看指标、研究、项目评估、全球趋势；与国内政策层的证据类型不同。
3. **公益机构与执行层**：救助儿童会中国、壹基金、基金会中心网、乡村发展基金会、儿童少年基金会、民间组织。重点看项目、服务与一线实践。
4. **行业生态与合作层**：公益时报、中国发展简报、慈善联合会、邮件简报、招投标与基金合作机会。重点看行业生态与实际资源链接。
5. **社会事件与公共舆情层**：新闻媒体、司法案例、跨平台搜索、特定事件跟踪。重点看事实进展、社会反应及被忽视的问题。

五层可交叉：同一个儿童虐待案例可能同时来自最高检公示、公益组织行动、媒体报道和搜索信号；它们的**来源身份不同、可信度不同、贡献不同**，但都能指向同一事件。

### 9.1 分层不是越多越好

一套好信源系统应回答：来源是谁？为何收录？从哪里抓？多久更新？是否可靠？是否允许采？有无更合适的替代通道？**有“域名已加”不等于采集成功，有“采集成功”不等于内容被选用。**

## 10. 新增信源标准作业流程（SOP）

**第 0 步：说明为什么需要它。** 写下机构／主题、准备监测的栏目、潜在读者、跟既有来源的差异、预期信息量。

**第 1 步：识别采集类型。** 真 RSS 选 RSS；静态 HTML 列表选 `web_list`；可合法调用的 JSON 选 `json_list`；只有主题词能覆盖时再用 `search`；需要登录、验证码或强制拒接的来源不可绕过采集限制。

**第 2 步：创建候选并试抓。** 在后台“信源 → 发现候选 / 新建信源”中登记明确来源 URL、唯一 ID、所属机构、主题、版权边界。验证最近至少 5 条：标题、原文链接、真实日期、是否夹带导航或站内广告；核对 403/412/521 与重定向等失败。

**第 3 步：安全试运行。** 起始暂停或隔离；验证解析器选择器、第一次回填上限、按文章去重与 URL 标准化；确认不会误把旧年鉴、往期导航、目录封面当成本期内容。

**第 4 步：进入分析与验收。** 验证真实采集、分析队列、精选入池；记录“采到多少、独立多少、合格多少、为什么未入选”。尤其要区分“源已接通但 0 入选”与“抓取本身失败”。

**第 5 步：监测与调整。** 先少量上线，观察 48 小时及至少一个完整发布周期：成功率、入池率、最新文章延迟、重复率、模型开销、付费调用回执。不能因单次成功就长期无人监管。

**第 6 步：保留证据。** 写入来源登记、时间、URL、解析方式、测试结果、版权及许可复核、改动人、关联 PR、回滚方案。对不适合的来源保留“为什么否决”的证据，减少下次重复试错。

## 11. 两种很容易被误判的采集失败

**网站抓到了，但没有内容**：可能是机构主页而非新闻列表、选到导航链接、JS 渲染前无文章、日期格式错误、重复旧稿；需要调整目标栏目或解析器，不一定要加模型预算。

**网站能抓到数十篇，但入池为 0**：可能是综合媒体噪音、与公益主题无关、引用的是旧闻或转载、评分低于门槛。2026-10-23 SPA 站点试验中，世界银行儿童相关页面 8 条样本有 4 条入选；澎湃、财新、UNESCO 等部分样本一度 0 入选，证明技术接通并非业务价值。

**公众号等付费信源**：过去通过 EveryInfra、Dajiala、WeRSS 等途径试验；最新 README 明确公众号、微博等通道已经暂停，WeRSS 自 2026-10-25 起暂停。不能依据旧的 `enabled:true` 种子配置就宣称某条付费公众号现在持续运行；以生产数据和付费预算表为准。暂停第三方付费渠道也减少反复额度错误的运营噪声。

## 12. 内容筛选与 AI 编辑的完整链路

```text
发现候选 → 抓取正文/元数据 → URL 与内容去重 → 公益相关性预筛
                                               ↓
                                      评分 / 入选判定
                                               ↓
                           按需要写中文标题摘要与结构化字段
                                               ↓
                               同一事件归组、质量门槛
                                               ↓
                         动态 / 热点 / 主题 / 报告 / RSS / API
```

**预筛（PASS/BLOCK/UNKNOWN）**：宽召回，明显无关才拦；尤其儿童侵害、司法救助、妇女权益等不能仅因不是慈善机构新闻就误判为普通社会新闻。预筛阻断意味着不会进入公开内容流，但应保留后台解释与必要复核能力。

**评分**：依据来源等级和内容判断规则，采用独立评分及灰区复核，最终与当次有效门槛比较。2026-10-29 之后引入了减费逻辑，**不是每篇文章必定“固定五次付费 DeepSeek 调用”**：部分评分、结构化步骤在明显不满足条件时可跳过。旧成本文档的“五次”是历史结构示意，不能作为 11 月每篇精确模型请求数。

**写作与结构化**：入选／接近入选的内容可能进行更充分的“理解”，其他采用短摘要；分类、事实和主体识别要建立明确证据，不能把“文章提到某机构”自动变成“该机构正式发布”。

**事件归组**：将不同来源对同一个事实的报道集中，区分同一事实、同一故事进展及无关事件。时间较久的文章可以挂靠已有事件，但不能无条件创造“当前热点”。

**公开发布**：统一从 `packages/backend/src/publication/` 输出，网站、RSS、API、MCP 等共享规则；**读者打开网页不会直接触发一次 DeepSeek 计费**。

## 13. 热点、归组与时间衰减的阅读方法

热度一般以近 48 小时的信号为核心，内容少时可以放宽至 72 小时；24 小时衰减半程。正规来源是事件上榜的约束，网页搜索不是独立“官方确认”。多个同一站点结果只反映一次站点参与，不可按“文章篇数 × 媒体数”凭空放大。若某条热门信息涉及儿童隐私、尚未证实的指控或快速变化的司法进度，应以最新原文核实并及时纠错。

## 14. 每日、每周、每月总报

以当前 `apps/worker/src/schedules.ts` 为准（**北京时间 Asia/Shanghai**）：

| 任务 | 默认调度 | 解释 |
|---|---|---|
| 每日报告 | 每日 **08:00**（依功能开关） | 归整日报内容；可能不直接占据主要导航 |
| 周报 | 每周一 **06:00** | 生成上一期周报；刻意安排在高峰前 |
| 月报 | 每月 1 日 **06:30** | 生成上月月报 |
| 上一期周报补编 | 周一 **05:50** | 补齐迟到的上期材料；保留修订历史 |
| 上一期月报补编 | 1 日 **06:20** | 根据晚到资料补修订 |
| 缺失报告补齐 | 部分低峰小时的 **:15** | 避免在双倍费时段集中重跑 |

**给读者**：总报是一个时间窗口里经过整理的版本，不是对单条事实的最终判断。若发现某条漏报，应先确认是否属于旧文回补、跨期晚到、未通过精选、归组等待或版权限制，不能只看“抓取日期”。

## 15. 运营看板：怎样判断系统是否真的有用

建议至少同时看八组指标，而不只看“今日采到了多少”：

| 维度 | 建议指标 | 风险信号 |
|---|---|---|
| 覆盖 | 启用源数、有效机构数、原创主体数、领域覆盖 | 信源很多但高度重复 |
| 新鲜 | 原文发布时间→入库延迟中位数 / P95 | 热榜不断推两三天前的消息 |
| 可用 | 抓取成功率、有效 URL 比率、日期解析率 | 0 错误但内容多年未更新 |
| 内容 | 预筛通过率、入选率、抽样精准率、误杀率 | 单一主题 0 入池或异常刷屏 |
| 事件 | 同事同案合并率、不同主体证据数 | 一件事出现十张卡 |
| 审计 | 纠错处理时效、误归类复核、原文可访问率 | “来源可信”但点击打不开 |
| 费用 | 模型实际账单、搜索回执、每篇有效入选成本 | 新源回填与日常消费混算 |
| 可靠性 | 队列最老等待、重试中比例、备份验证 | 首页能开但已停止更新 |

注意两个分母：“入库”是抓到且保存的文章，“入选”是通过发布规则的文章；它们都不等于独立事件数。与科研评估一样，**产出数量只是观测指标，能否核验和复用才是系统价值的核心**。

## 16. 费用、价格单位与增长压力

### 16.1 付费结构

**固定费用**：腾讯云主机历史促销支出 ¥99/年（¥8.25/月），续费报价可能显著不同；域名、备份和运营人工应独立估价。**变动费用**：DeepSeek 模型 Token、DeepSeek 网页搜索请求，以及只在启用时才会发生的第三方社交采集 API。RSS / 免费官网轮询不收第三方 API 请求费，但仍消耗 CPU、网络、存储、AI 分析。

**计价单位必须分清**：模型价以“人民币／100 万 Token”为单位；网页搜索以“人民币／成功调用”为单位；外币采集费必须保留原币种和实际回执，不得将 `$0.65` 直接当成 `¥0.65` 加总。项目历史曾有多币种汇总问题，新版 `providers/pricing.ts` 和 `admin/usage.ts` 应作为计算基准，仍需与平台账单核对。

### 16.2 可引用的历史单价（10 月 31 日）

| 项目 | 空闲价 | 高峰价 | 说明 |
|---|---:|---:|---|
| DeepSeek Flash 未命中输入 | ¥1 / 百万 Token | ¥2 / 百万 Token | 北京工作日 9–12、14–18 高峰 |
| DeepSeek Flash 缓存命中输入 | ¥0.02 / 百万 | ¥0.04 / 百万 | 提示词稳定有利于命中缓存 |
| DeepSeek Flash 输出 | ¥4 / 百万 | ¥8 / 百万 | 输出贵于输入 |
| DeepSeek 网页搜索 | ¥0.005 / 次 | 相同 | 以成功调用计费 |

这是生产价格表 **10 月 31 日快照**，不是 11 月 9 日厂商实时公布价格或今天的结算账单。

### 16.3 三种预算口径，不能混为一谈

1. **历史支出**：按实际 receipts + 服务商账单核对。
2. **稳态速率预算**：10-31 近 7 天速率约 ¥119/月（模型+搜索）；加上优惠服务器约 ¥127/月。此时尚未完全体现 11-02 的 AnyDoor 调整。
3. **扩张预算**：10-31 粗估增加一个搜索源每月约 ¥1.50、一个官网列表源约 ¥0.22；作为经营规划，不是单条源的合同价格，更不应机械乘以每条来源。模型分流后须重新测算。

**11 月 2 日变化**：预筛和普通摘要默认由本地 AnyDoor 网关选择免费池（历史实测多为 Qwen 系列），其他任务仍使用 DeepSeek Flash；若网关身份认证失败可回退，429 等暂时错误仍可能让队列退避。**这将改变当前的有效单位成本**，因此任何“月费 ¥127”应标成调整前的参考，不可当作当前结算金额。

### 16.4 给运营的费用决策树

想加源 → 先判**免费官网还是付费 API** → 估计每天新文章数 → 判断每条新文章实际需经过哪些模型步骤 → 查看历史回填数量与队列容量 → 留预算和回滚路径。搜索源 72 个每天运行，按 2026-11-02 记录约 540 次网页检索/天、检索费约 ¥2.7/天；它是搜索 API 的费用，**不是整套 YiHot 模型与服务器总成本**。

**预算护栏**：按分钟/小时/滚动 24 小时限制付费调用；历史稿另有日配额、积压容量和可归档机制。截止版本的文档中存在不同时点额度（例如模型日上限 6,000 与旧报价里的 9,000，搜索日上限 500 与 900），**执行时只读取生产数据库 `budgets` 的当前值，不把任何历史文档数字当成最新保险丝**。超过配额通常是延迟而不是“必须加钱”。

## 18. 生产部署与环境边界

当前运维资料给出的生产拓扑为腾讯云北京 Ubuntu、Docker Compose；PostgreSQL、API、Worker、Web 为核心组件，`setup` 负责迁移和种子初始化。邮件采集和投递另外由 systemd 定时器承担；WeRSS 是额外容器／会话依赖，当前采集业务已暂停，不可盲目重启后宣称恢复。

**一份代码有三份状态**：开发机文件、GitHub `main`、腾讯云实际镜像／配置。只有三者核验一致，才能说“功能已上线”。GitHub 提交与 Actions 绿勾只是代码检查通过；生产还需要对照文件版本、镜像 ID、服务状态和真实页面。生产 `.env` 不在 GitHub 中。`industry/sources.json` 的“启用”只影响新 seed 插入，已存在数据库行以运行态配置为准。

**部署纪律（维护者必须记住）**：

1. 有独立测试或灰度环境时优先验证，避免直接修改生产。
2. 检查当前工作区与 GitHub 的差异，先确认用户另一台电脑或其他 Agent 没有未同步修改。
3. 备份数据和必要配置，且不要把明文密钥带入 CI／公开仓库。
4. 需要代码改动时构建新镜像并通过 Compose 重建；**不要采用 `docker cp + restart` 这种临时补丁**，它在重建后会静默丢失。
5. 验证 Web/API/Worker 和数据库连接，再查内容、邮件与报告；对 FutureMe 反代和邮件任务的影响单独验收。
6. 提交验收记录：Git commit、测试结果、部署时间、回滚办法、生产回执与异常。

**源码已经存在但容易误导人的地方**：README 的快速开始同时出现 `cp .env.example .env` 与 `node scripts/init-env.ts`，而当前 `init-env.ts` 在 `.env` 已存在时会拒绝覆盖。新手应**二选一**：先从示例复制并自行配置，或只用初始化脚本生成；不要无脑连续执行这两个步骤。

## 19. 队列、容量背压与“为什么几小时不更新”

YiHot 通过 PostgreSQL 内的 `pg-boss` 管理任务。典型阶段包括信源抓取、正文提取、预筛/分析、翻译、事件归组、热度、报告和投递。**“新文章还没上首页”至少可能发生在采集、正文、预算、模型、选题、分组、发布时间或公开发布任一环节**。

### 19.1 三个不同的“停下来了”

- **预算等待**：模型/搜索调用达到每分钟、每小时或滚动 24 小时额度。系统可退避，通常会随窗口滚动恢复；这不是内容永久失败。
- **服务商拒绝**：HTTP 402 余额不足、401 凭据失效、429 速率限制、5xx 暂时故障。2026-10-30 后新出现的部分 DeepSeek 402 会进入冷却，避免每篇立即重撞收费接口；**不要沿用旧版“看到 402 就直接全库重置”的处置法**。
- **容量归档**：历史稿超过日上限（默认约 120 篇）、积压（约 600 篇）或等待（约 96 小时）时可能转为 `archived`。这是保留原始记录、暂不付费分析，**不是删除**。政策、法规、司法、研究类标题有特例，不应机械按“旧”丢弃。

### 19.2 队列常态检查

先看过去 24 小时新增多少、完成多少、归档多少，再看最老等待时间与日终积压是否连续 3 天增长。**“有积压”本身不是故障**；稳定、可预期地清空比永远 0 排队更重要。需警惕免费模型池 429 导致指数退避（可能长至约 40 分钟）、人工批量重跑和新源首采突发。

### 19.3 运行监控节奏

源码 `apps/worker/src/schedules.ts` 显示：内容扫尾、翻译、热点排名每 5 分钟检查；信源到期调度每分钟；运维恢复与告警每 10 分钟；日常小结及周一信源健康报告另有时刻。Worker 自行写心跳，API 中守护进程检测 **约 30 分钟未更新的 Worker 心跳**并尝试发一次告警和恢复提示；这不同于“某个任务因预算限流暂时没有新文章”，不应将预算等待误判为 Worker 已死。

## 20. 模型选择：DeepSeek Flash 与 AnyDoor

### 20.1 模型并非整条队列只有一种

各环节可以分别选择 `prefilter`、`score`、`understand`、`summarize`、`structure`、`group`、`groupReview`、`digest`、`report`、`translate`、`monitor` 模型。选择优先级是 **后台管理员覆盖 > 每阶段环境变量 > 默认模型**；后台更改会按缓存策略影响后续任务，不自动重算历史成果。

**按 2026-11-02 记录**：`PREFILTER_MODEL=anydoor-auto`、`SUMMARIZE_MODEL=anydoor-auto` 用本机 AnyDoor 免费池；其他阶段主要为 `deepseek-flash`。此为“当时上线的配置记载”，不能推断 11 月 9 日每个模型路由仍不变。进入后台“模型与评测”逐项检查，是唯一可靠的现场动作。

**AnyDoor 不等于免费且无风险**：网关本身可能 401、429、单上游不可用；配置错误可能导致回退到 DeepSeek 并产生费用，虽然文章继续处理，运营却误以为仍在免费池。应按阶段分别看实际 `receipt_attempts.service/model`，并看服务商余额。对重要研究、未成年人保护案件的自动摘要应采用定期人工评测，防止低成本模型带来漏报、误写和错引。

### 20.2 成本与质量的最小对照实验

从近期真实内容中分层抽取至少 50–100 条（政府政策、儿童权益个案、公益机构、媒体转载、英文研究、容易误判的反例）。针对候选模型记录：预筛召回率、错误拦截率、摘要关键事实准确率、JSON 解析成功率、平均/95 分位延迟、每条实付成本。不要只在 5 篇“简单稿”上成功就将所有步骤整体切换。

## 21. 后台每一页做什么：管理员任务矩阵

| 管理页面 | 核心操作 | 操作前检查 | 操作后验收 |
|---|---|---|---|
| 内容诊断 | 查某条文章的处理过程、原因、异常 | 文章原文、日期、URL、是否重复 | 分析状态与最终公开卡片一致 |
| 信源 | 浏览状态、暂停/恢复、预览、调频 | URL、版权、当期真实内容、失效原因 | 抓取成功＋有效入池＋费用合理 |
| 候选／新建信源 | 登记新来源与解析配置 | 与既有来源有无重叠、合法性 | 按第 10 章验收，而非“添加成功” |
| 运行 | 看定时任务、队列状态和错误 | Worker 心跳、余额、预算、时区 | 积压停止增长，故障可复现且可恢复 |
| 用量与成本 | 看 Token、调用次数、实付与估算 | 币种、峰谷单价、cache_hit、回执来源 | 与供应商账单一致，不能直接混币 |
| 模型与评测 | 查看各阶段路由、成功率、试验比较 | 当前生产模型、API Key 和样本 | 性能、质量、成本均有验证 |
| 订阅 | 看邮件确认、活跃与退订、退信 | 订阅隐私、SMTP 状态 | 只有确认订阅者收到对应周期报告 |
| 反馈 | 处理纠错、版权或下架意见 | 具体页面和原始证据 | 必要时下架、更正、留审计 |
| 设置 | 预算上限、通知、二维码等 | 谁授权、风险和回滚方案 | 设置与运行态一致 |
| 审计 | 查询谁在什么时候改了什么 | 变更人、前后值 | 关键修改能解释和恢复 |

**原则**：对无法确认的变化，先观察和取证；涉及成本阈值、内容算法、历史重算或外部发布时，必须记录决策原因。重要的外部行动不要让 AI 在缺少权限审计时自主执行。

## 22. 故障排查：从“症状”而不是从“猜的原因”开始

| 读者看到的症状 | 先查什么 | 常见原因 | 禁止的错误处理 |
|---|---|---|---|
| 网站打不开 | Web 容器、反代、TLS、API 心跳 | 容器失败、证书或路由 | 直接删数据库 volume |
| 网站打开但停更 | Worker 心跳、最近采集、余额、预算 | 采集失败、402、429、队列背压 | 手改新闻发布日期假装有新稿 |
| 文章在库却看不到 | 预筛、评分、入选门槛、公开发布状态 | BLOCK、低分、分组待定 | 降低所有门槛掩盖错误 |
| 旧闻显示成今天 | `published_at`、日期精度、收录时刻 | 搜索回看、历史回填、解析缺日期 | 仅改前端文字，不修数据链 |
| 同案出现多张卡 | 事件归组、原始 URL、独立主体 | 多条同源文章未成功挂靠 | 直接删卡片、丢追溯 |
| 某源“正常”但没有稿 | 原站最近日期、source health、入池率 | 停更、解析了导航、低相关 | 只根据 health=ok 宣称高质量 |
| 周报少了内容 | 周期边界、归组完成、晚到补编 | 期末延迟、精选尚未完成 | 直接把历史稿当新一期 |
| 收不到周报邮件 | 双重确认、outbox、SMTP、退信 | 未确认、授权码失效、投递失败 | 重复全量群发造成骚扰 |
| 费用突然变多 | 新稿/回填/搜索三分账、实际回执 | 新源首采、批量重跑、搜索频率 | 直接把预算上调到无限 |
| 社交信源一直 0 | 渠道启停、余额、health、API 权限 | 已决定停服或预算为零 | 绕过授权抓取个人平台 |

**恢复顺序**：确认现象 → 查真实时区 → 看最近一次成功 → 判断费用闸门/服务商故障/代码缺陷 → 最小修复 → 小范围验证 → 观察一个周期 → 记录过程。对 HTTP 401/402/429、403/412/521、TLS 和 DNS 问题要区分，不要都叫“网络错误”。

## 23. 安全、隐私、版权与伦理

**采集合法性**：官方站点可读不等于可以批量转载全文。优先引用标题、摘要、原始链接；内容权限、robots/服务条款、公众号和社交平台访问控制要逐站核对。禁止凭修改 User-Agent、模拟身份或绕过验证码获取本无授权的内容。

**未成年人及公益受益人信息**：不得因“一条新闻可抓”就把未成年人身份、医疗信息、家庭地址、案件详细隐私传播给更多人。研究或项目分析中要区别公开报道与可供二次处理的个人数据；不把受害者隐私放到外部 AI 服务而无必要保护。

**用户数据**：订阅邮箱、退订状态、发送回执具有个人数据属性，最小化访问、限制保留期和数据导出；已读和收藏主要在本地浏览器保存。README 已提醒：公开隐私说明中的实际运营主体与联系信息仍需维护者核实完善，正式推广前应确认。

**凭据**：生产 `.env`、后台管理员密码、SSH、邮件授权码及第三方 API Key 只能通过安全渠道交接。仓库内的 `secrets/credentials.env.enc` 是密文备份，不代表可以分享解密口令；**解密口令与密文不能存同一处**。出现泄露时应先轮换密钥，再同步加密归档，不要只删 Git 提交。

**知识产权**：YiHot 基于 AIHOT 的 MIT 开源代码，继续保留 LICENSE、NOTICE 与第三方归属说明；AIHOT、救助儿童会及其他组织的名称、商标、Logo 各有独立权利，YiHot 不能表述为它们的官方发行版或背书产品。

## 24. 备份、恢复与长期交接

**要备份的不是“一个仓库”**：还包括 PostgreSQL 数据、已上传文件、运行配置、服务器代理、独立邮件服务配置和外部账单线索。代码在 GitHub 不等于数据库在 GitHub；没有可恢复的 DB dump，GitHub 仓库再完整也会丢失历史文章、队列与审计。

**已有机制**：代码支持定时 PostgreSQL 转储、文件打包、校验 SHA256、可配置腾讯云 COS（对象存储）上传；只有部署了所需备份凭据才会运行上传任务。脚本默认保留本地最近若干份，**备份存在 ≠ 已经测试恢复**。应至少每季度在隔离环境完整试恢复一次。

**跨人员交接必须包含**：①GitHub 权限②云资源权限③后台账号/密码交接方式④API 与邮件服务账号/密钥的安全管理⑤备份与恢复验证⑥财务充值和续费⑦最新信源与队列基线⑧当前已知故障⑨下一次巡检日期⑩退出与权限回收。离任者不应保留长期高权限账号。

# 附录 A · 14 个高频问题与简短回答

**Q1：YiHot 是救助儿童会官方网站吗？** 不是。它是基于开源项目定制的独立信息服务，聚焦儿童公益，不代表任何所收录机构的立场。  
**Q2：为什么我看到的是“全部动态”而不是“精选”？** 当前主首页优先使用 `/all`；精选评分仍在后台和报告链路中发挥作用。  
**Q3：为什么有条消息今天抓到、日期却在几天前？** 列表按原文发布日期展示，搜索回看是为了补漏。请分辨事件发生日、原文发布日和本站收录日。  
**Q4：为什么搜索源比官网源贵？** 主题搜索可能带来更多候选、并按查询调用收费；主要成本还取决于产生多少新文章需要 AI 分析。  
**Q5：为什么我明明加入官网，后台没有出现？** `sources.json` 是 seed，不会覆盖线上已有数据库记录；要看同步、迁移、seed 与生产是否真正运行。  
**Q6：页面能打开但没有今天新闻，是不是服务器坏了？** 不一定；先查当日真实新稿、Worker 心跳、预算、模型 402/429、预筛和原文日期。  
**Q7：AI 会把每篇都调用同一模型五次吗？** 旧流程基本按五步设计，现已加入条件跳过与 AnyDoor 分流；实际模型及费用以回执记录为准。  
**Q8：为什么换了模型，旧文章没变化？** 模型切换只影响下一次任务；历史结果不会自动全量重算。  
**Q9：公众号为什么没有内容？** 公众号/微博等付费及 WeRSS 通道在已知最新 README 中处于暂停状态，需要查当前授权、预算和运营决定。  
**Q10：能不能把某家网站全部抓进来？** 技术、许可和内容价值三项都要过关；全文采集与公开分发需要明确授权。  
**Q11：新增信源会导致永远积压吗？** 系统已有预算与容量背压、历史稿归档策略，但增加新稿仍可能拉高延迟。关键监测“新进—完成—归档”和最老等待。  
**Q12：用户订阅 1,000 人，会触发 1,000 次 AI 周报吗？** 不会。一次生成周期报告，投递给订阅者；增长主要增加 SMTP 与订阅管理压力。  
**Q13：是否可以只用 GitHub 恢复整个系统？** 不可以。还需要数据库备份、运行配置、外部账号、邮件服务以及部署拓扑。  
**Q14：什么是最重要的管理员原则？** **先看证据，再行动；先试抓，再启用；先核实费用和来源，再扩量；先备份，再改生产。**

## D.2 建议采用的唯一事实源顺序

1. **生产数据库、真实服务商账单与现场检测**：运行事实，必须给出检测时间和环境。
2. **GitHub 已合并的 `main` 代码**：实现能力，不等于生产已部署；以具体提交 SHA 绑定。
3. **近期专题实测文档**：可以帮助解释原因，但需保留快照日期。
4. **长期维护手册和历史会话**：流程和经验，不能直接代表当前金额、模型、预算、信源总数。
5. **规划设计、候选台账、未合并 PR**：只能称为“计划／候选”，不可以写成“已上线”。

> **报告结语**：YiHot 的成熟，不是信源从 100 条涨到 200 条，也不是一天处理 5,000 篇，而是让重要信息能够被**发现、归类、溯源、核验、及时更正、控制费用，并被下一位维护者无缝接手**。一套经得起检查的公益信息系统，比一张永远显示“运行正常”的漂亮看板更有价值。

**文档完成标记**：`使用手册文字版 1.0`。今后如果生产现场数据发生变化，应更新具体快照段落，而不是直接删掉历史数字；PPT 的数值应与本报告同一版本同步更新。
