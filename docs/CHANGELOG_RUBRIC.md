# 更新日志的取舍标准

更新日志（`industry/changelog.json`）登记的是**读者在页面上能察觉的变化**，不是提交清单。每次改动都写进去，读者要看的东西就被工程细节淹了；但漏写又会让人找不到入口、以为站点坏了。这份标准把「写不写」变成可以算的四个维度，避免每次凭感觉。

格式与字数由 `scripts/changelog-check.mjs` 强制（标题 ≤32 字、正文 ≤2 行、每行 ≤70 字、合计 ≤110 字、禁内部用语）。本文件只管**选材**。

## 四个维度

| 维度 | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| **V 可见度** | 只有后台、文档、CI 能看到 | 特定页面里能看到，但不常经过 | 常用页面上能看到（列表、侧栏、订阅页） | 一进门就看得到（首页、报头、标签页、底部导航） |
| **H 改变习惯** | 读者不用改任何动作 | 略有不同，不影响找到东西 | 名称、位置或入口变了，照旧找会落空 | 原有功能消失，或换了一套用法 |
| **B 覆盖面** | 单个页面的一处细节 | 一类页面 | — | 全站 |
| **P 可感知** | 要对对比或读代码才知道 | 留意得到 | 一眼就看出来 | — |

总分 0–10。**H 权重最重**：一项改动再小，只要让读者原来的路径失效，就必须写——那是「找不到」的来源，而不是「不知道」。

## 阈值与处置

| 得分 | 处置 |
|---|---|
| **7–10** | 必写，独立成条 |
| **4–6** | 写，但并进最相关的那一条，不单独占位 |
| **0–3** | 不写。只在提交信息和 `MAINTENANCE.md` 留痕 |

两条硬规则压在上面：

1. **同一处界面在一周内反复调，合成一条。** 读者不关心改了三轮，只关心最后什么样。
2. **已经公告过的状态变化不再重复。** 「暂停」变「正式停用」对读者没有新信息。

## 判定流程

1. `git log --pretty=format:"%h|%ad|%s" --date=format:"%m-%d %H:%M" --since=<上一条日志的日期>`
2. 剔掉 `docs`、`ci`、`test`、`chore` 纯工程提交。
3. 剩下每条问一句：**读者能不能在页面上看到？** 看不到直接判 0 分，不必再打其余三项。
4. 能看到的四项打分，按阈值决定写 / 并 / 不写。
5. 同一处界面合并成一条，再按格式卡校验：`node scripts/changelog-check.mjs`
6. 上线后核对两处：`/api/site/changelog` 的首条与 `latestVersion` 一致，`/changelog` 页面确实渲染出来。

> `latestVersion` 必须等于第一条的 `date` + `time`，否则侧栏的更新红点不会亮。日志由 API 在**模块级缓存**中读取（`packages/backend/src/site/meta.ts`），只改 JSON 不重建镜像不会生效。

## 成稿要求

- 写愿望达成后的样子，不写「以前为什么不行」。原因留在提交信息里。
- 一句一个事实，最多两句。第三句通常是把来龙去脉又交代了一遍。
- 用读者页面上的名字：说「周次框」不说「报眼」，说「标签页图标」不说「favicon」。
- 数字要能对得上页面（条数、期数），别写「若干」「大量」。
