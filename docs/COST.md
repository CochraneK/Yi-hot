# 花的钱去哪了（成本口径）

> 2026-10-24 起的口径。手里只有一句"钱没了"时，先跑 `scripts/cost-report.ts`，再谈优化。

## 一、先分清两种花费

站点上真金白银的只有两项：模型调用（`llm`）与网页搜索（`deepseek-tools`，¥0.005/次成功请求）。
同一个 `¥10`，可能是完全不同的两件事：

| 类型 | 什么时候发生 | 近 7 天实测 | 性质 |
| :--- | :--- | :--- | :--- |
| **今天的新闻**（`articles.backfill = false`） | 每个采集周期新进来的稿 | **¥0.26–1.38/天**，单篇 ¥0.0016 | 日常成本，随更新量线性 |
| **补历史**（`articles.backfill = true`） | 只有**第一次采一个新源**时 | 10-23 ¥12.14 / 10-20 ¥4.06 / 10-24 ¥2.85 | **一次性**，加源才有 |
| 网页搜索 | 搜索类源每轮查询 | ¥0–1.96/天 | 按次计费 |

**所以「每天成本太高」通常是个错觉**：日常出稿一天不到一元；某天突然掉十块，那天一定加了新源
（首采回填），或者有一批历史稿被重跑（例如 402 失败重入队）。

## 二、单篇为什么是这个价：五步、五次调用

一篇文章进来到判定完，固定五次模型调用，与文章长短关系不大：

| 步骤 | 用途 | 次数/篇 | 典型花费 |
| :--- | :--- | ---: | ---: |
| `prefilter_article` | 先判是不是本站在意的事（不行就到此为止） | 1 | ¥0.0015 |
| `score_article` | 关注度打分（**两次取样**再平均，抗抖动） | 2 | ¥0.0008 ×2 |
| `summarize_article` 或 `understand_article` | 写中文标题与摘要；接近入池的走 understand（更贵更细） | 1 | ¥0.0014 / ¥0.0026 |
| `structure_article` | 归类、标签、事实三元组 | 1 | ¥0.0017 |
| 合计 | | **5** | **¥0.003–0.007** |

单价来自 `service_prices`（CNY，**每百万 token**）：

- 输入未命中缓存 ¥1.00、**命中缓存 ¥0.02**（差 50 倍，所以提示词前缀要稳定）、输出 ¥4.00。
- **高峰价 ×2**：北京时间**工作日 9–12、14–18**，同一个模型走 `model@peak` 那一行。
  实测 10-23 15 点那一小时 ¥0.00192/次，18 点那一小时 ¥0.00115/次——**同一批活，贵 1.7 倍**。
- 因此：**补历史、批量重跑安排在夜间或周末**，同样的钱能做将近两倍的量。

## 三、首采补的是哪一段（不是"从建档开始补"）

这是最容易被误解的一处。**补的不是"这个源历史上所有新闻"，而是它列表页上最靠前的 8 条**，
再被两道闸门夹住。三重限制同时生效：

| 闸门 | 默认值 | 代码位置 | 作用 |
| :--- | :--- | :--- | :--- |
| 条数 `initialBackfillLimit` | search 12 / 其余 8 | `collect.ts` 首采分支 | 一轮最多收这么多条 |
| 时间窗 `initialBackfillMonths` | 12 个月 | 同上，`cutoff = now - 12×30 天` | 早于一年前的**带日期**条目直接丢 |
| 增量闸门 `ingestMaxAgeDays` | 365 天 | `collect.ts` 增量分支 | 之后每轮仍不许进一年前的老稿 |

**所以"10 年后新增信源会不会补 10 年"——不会。** 无论这个源存在了 10 年还是 20 年，
首采只拿列表页最上面那几条（上限 8），且必须落在最近 12 个月内。真正的天花板其实是
**列表页本身有多深**：绝大多数政府站只放 20–50 条，想多拿也没有。

实测跨度（2026-10-24 那批 8 个新源，`articles.backfill = true`）：

| 源类型 | 实际跨度 | 原因 |
| :--- | :--- | :--- |
| 搜索源（`kind='search'`） | **4–8 天** | `lookbackDays: 7`，比 12 个月窗严得多 |
| 网页直连、日更站 | 1–2 周 | 列表 8 条就是最近 8 天 |
| 网页直连、慢更站 | 3–9 个月 | 列表更新慢，8 条能回溯到年初（妇儿工委 2026-02-02 起） |
| RSS | **可能几年** | 见下方"两个泄漏" |

### 两个真实存在的泄漏（2026-10-24 已修）

闸门对**解析不出日期**的条目原来是放行的（`!c.publishedAt ||` —— 无日期的按收录时间落位，
这是落位口径决定的）。归档页面上"列表不给日期"的老条目因此能混进来：

- **RSS 整份重读**：配置变更会丢掉 etag，feed 从头读一遍。`rss-who-news` 因此一轮进了 73 条，
  最早 **2020-04-20**（跨度 2364 天）。
- **无日期归档条目**：`web-probe-mzt-*` 三个民政厅探测源共 49 条，最早 **2018-05-18**。

修之前的规模（近 30 天入库 4451 篇）：

| 指标 | 数值 |
| :--- | ---: |
| 原文日期早于 12 个月的条目 | **147 篇（3.3%）** |
| 其中已入池（会出现在时间线上） | **39 篇** |
| 早于 24 个月 | 109 篇 |
| 最老一条 | 2018-05-18 |

钱上不痛（147 × ¥0.004 ≈ ¥0.6），痛的是**内容**：几年前的稿子按收录时间落位，
会被读者当成今天的新闻。

现在的判据（`listPrintsDates`，首采与增量都过）：**本轮候选里过半且至少 3 条带日期，
说明这个列表是"给日期"的，无日期的条目一律当归档丢弃；整轮都没日期才保持放行**——
那种站只能靠详情页拿时间，全拦掉等于把这个源清空。两条边界都有测试
（`tests/listings.test.ts` 的两个新用例：一条验归档被丢，一条验不误杀）。

已经进库的 147 篇没有回删（它们是真实文章，只是日期老）；`scripts/cost-report.ts` 的
闸门体检会继续报这个数，修好了就不会再涨。

## 四、加一个源大概要花多少

首采回填条数由 `config._aihot.initialBackfillLimit` 决定：`sources.json` 里每个源都显式写了
**search 12 / 其余 8**（3 个 UNICEF 源 6），代码兜底也是 8（原来是 30——漏写一个源就多付三倍）。

```
一次性成本 ≈ initialBackfillLimit × 单篇均价（¥0.004） × 源数量
```

- 按旧值（search 30、web 10–12）加 30 个源：约 `30 × 0.004 × 30 ≈ ¥3.6` 起，实际因去重和解析失败常到 ¥5–8。
- 按新值加 8 个源：约 `8 × 0.004 × 8 ≈ ¥0.26`，实测 10-24 全批（含 97 篇搜索稿）回填 ¥2.85，
  其中一多半是 402 失败重跑的 **316 篇存量稿**，不是新源本身。

## 五、护栏（已生效）

| 护栏 | 值 | 效果 |
| :--- | :--- | :--- |
| `budgets.llm.per_day` | 40000 → **6000**（滚动 24 小时） | 一天最多约 **¥9–11**（高峰口径），超出即暂停付费调用 |
| `budgets.llm.per_hour` | 6000 → **1200**（2026-10-24 回落） | 单小时上限约 ¥2.2，防止一次误操作把全天额度烧掉 |
| `budgets.deepseek-tools.per_day` | 800 → **500**（隔天跑后约 210 次/天） | 搜索一天最多 ¥2.5 |
| 高峰限流 `ANALYZE_PEAK_PER_HOUR` | 8/小时 | 高峰时段只放行少量，批量自然落到半价窗口 |
| `initialBackfillLimit` | search 12、其余 8（兜底也从 30 改成 8） | 新源首采成本降到原来的 1/3 左右 |
| 历史回填只在半价时段 | 高峰 0 放行（当日新闻保留溢流） | 回填不再撞双倍价，见 5.3 |
| **历史日上限** `HISTORY_DAILY_MAX` | 120 篇/天 | 超出即归档（不是排队），见 [QUEUE_SUSTAINABILITY.md](QUEUE_SUSTAINABILITY.md) |
| **历史积压背压** `HISTORY_BACKLOG_MAX` | 600 篇 / 等待 96 小时 | 装不下就不再接收新的历史候选 |
| **搜索隔天跑** `config.everyNDays` | 搜索源 2（零产出源 3） | 搜索 API 从 ¥2/天 降到约 ¥1/天，回看窗口不变 |

被护栏挡住**不是失败**：`BudgetExceededError` 是可重试的，文章留在队列里，等窗口滚动后自动继续。
被**容量闸门**挡下则是另一回事：历史稿会进 `archived`（保留原文，可一键放回），
当日新闻永不被挡。两套机制的取舍与容量缺口计算见 [QUEUE_SUSTAINABILITY.md](QUEUE_SUSTAINABILITY.md)。

### 5.1 批量加源那天：开「加源窗口」而不是关护栏

`per_day` 比的是**过去 24 小时**的调用数，不是"今天零点以来"。所以批量日之后的一天，窗口里还压着
昨天那批的量——直接按常态值（6000）回落，会把白天的新稿全卡在队列里。正确做法是给"新增额度"：

```bash
node scripts/cost-window.ts            # 现在多少、今天花了多少、还能分析多少篇
node scripts/cost-window.ts batch      # 在"已用"之上再加 6000 次（约 ¥4.8、1200 篇）
node scripts/cost-window.ts batch 9000 # 再给 9000 次
node scripts/cost-window.ts normal     # 跑完回落 1500/6000
```

`batch` 会把 `per_day` 设成 `当前 24 小时已用 + 新增额度`，所以它给的是**一次性预算**，与历史无关；
`status` 在额度高于常态时会打印提醒，忘关一眼看得出来。**跑完必须回落。**

### 5.2 加一批源到底花多少

| 项 | 公式 | 20 个省残联的例子 |
| :--- | :--- | :--- |
| 首采一次性 | 源数 × 回填条数(8) × ¥0.004 | 20 × 8 × 0.004 ≈ **¥0.64** |
| 日常增量 | 日增稿数 × ¥0.002 | 20–40 篇/天 ≈ **¥0.04–0.08/天** |
| 月增 | 上项 × 30 | 约 **¥1.5–2.5/月** |

也就是说：**加源本身几乎不花钱，贵的是"这些源每天带来多少稿"**。真正要盯的是每日新稿量，
不是源的数量。反过来说，为了省钱去砍零入池的源是没用的——22 个零入池源近 14 天只占 263 篇（6%）。

### 5.3 回填只在半价时段跑（2026-10-24 生效）

当日新闻和历史回填的取舍本来不同：前者有人等着看，后者按定义就是几周前的稿，晚几小时一点损失都没有。
所以工作日高峰（北京 9–12、14–18）只放当日新闻，回填稿一律等半价窗口：

| | 高峰 | 低谷 / 周末 |
| :--- | :--- | :--- |
| 当日新闻 | 每小时 `ANALYZE_PEAK_PER_HOUR` 篇（默认 8） | 不限 |
| 历史回填 | **0**（人工重算 `attemptTag` 除外） | 不限 |

实测依据：近 30 天回填总花费 ¥31.67，其中 **¥9.93（31%）落在高峰时段**，这部分是本可避免的双倍价。
挪到低谷后同样的活只需 ¥4.97，30 天省约 ¥5。数额不大，但零效果损失——回填稿本来就不着急。

同一原则也用在报告上：`reports.weekly` 周一 10:00 → **06:00**，`reports.monthly` 1 号 10:30 → **06:30**，
`reports.catch-up` 从每小时改成只在半价小时（0–8、12–13、18–23）检查。日报仍是 08:00（本来就在低谷）。

**注意**：这条只影响「什么时候付钱」，不影响落位与时效。`discovered_at` / `published_at` 在入库时就写好了，
延迟分析不会让稿子的时间变晚；当日新闻照旧随时处理。

## 六、怎么自己看账
```bash
# 宿主机上，在 worker 容器里跑（默认近 7 天）
sudo docker exec aihot-worker-1 node scripts/cost-report.ts 7
```

输出三段：按天拆「今天的新闻 / 补历史 / 搜索」、按步骤拆占比、以及单篇均价与当前护栏值。

**判据**：只看「今天的新闻」那一列判断日常成本；「补历史」那一列是加源的账，单独看。

## 七、还能再省的地方（未做，按性价比排序）

1. **`structure_article` 只为将入池的稿跑**：现在只要 prefilter 不拦就会跑，等于给三分之二不会上站的稿
   白付 ¥0.0017/篇。改完约省 20%（需先确认 `fact` 不参与未入池稿的分组）。
2. **`prefilter` 只喂标题 + 摘要 + 正文前 800 字**：目前 2025 token 里大半是正文，判断"在不在题"用不着全文，
   约省 15%。
3. **`SCORE_CALLS` 2 → 1**：省 20%，但打分稳定性下降，需先用 `scripts/eval-selection.ts` 对齐阈值，不建议先动。
4. **停掉零入池源**：22 个源近 14 天零入池，但合计只占 263 篇（6%），省不下钱——**别从这里动手**。

已经做完的两条，别再翻出来当新方案：把回填挪到半价时段（5.3，省约 ¥5/月）、
代码兜底的 `initialBackfillLimit` 30 → 8（防漏配，没有存量影响）。
把 8 篇继续降到 4 篇没有必要：加 20 个源首采 160 篇 ≈ ¥0.64，砍一半只省三毛。
