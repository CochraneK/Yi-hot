## 网站「内容停更 16 小时」故障排查与恢复

**现象**：页面能打开（各路由 200、静态资源正常），但北京 10-24 08 点之后基本没有新内容。

**定位路径**（这套顺序最快，下次照着走）：
1. `docker ps` 看容器 → 都 Up，无异常。
2. 站点 `/` 与 `/yihot/` 都 200（`/yihot/` → `/yihot/all` 是**正常**重定向，不是故障）。
3. `SELECT max(created_at) FROM analyses` → 停在 16 小时前；而 `articles` 仍在入库
   → 结论：**采集正常、分析停摆**。
4. `receipt_attempts WHERE service='llm'` 按小时统计 → 北京 01 点 2568、02 点 810、
   **03 点 4085**，08 点后归零。24h 滚动窗口合计 **7722 次 > 额度 6000** → **额度被吃满**。
5. `articles WHERE processing_state='new'` 全部带 `processing_retry_at`（多数在未来）
   → 是预算耗尽后的**退避**在排队，不是死锁。

**根因**：昨夜北京 01–03 点那波回填（闸门部署前的旧行为）一次吃掉全天 LLM 额度，
之后当日新闻也被一起挡住 —— **额度是所有内容共享的，历史能把当日新闻挤掉**。

**处置**：
1. `budgets.llm.per_day` 6000 → 9000（护栏余量；实际花费仍由 `HISTORY_DAILY_MAX=120` 管住）。
2. `UPDATE articles SET processing_retry_at=NULL WHERE processing_state='new' AND NOT backfill
   AND processing_retry_at > now()` → 只给**当日新闻**解除退避（151 篇），历史继续排队。
   效果：pending 215 → 42（只剩历史稿），publications 5425 → 5460。

**顺带确认闸门已在线上生效**：`processing_state='archived'` 已 222 篇（昨天还是 0，
因为当时队列里根本没有历史稿可拦）。

**仍在的已知问题（未处理）**：`budgets.everyinfra.per_day=0` → 8 公众号 + 3 微博 + 3 小红书
共 14 个源持续失败（近 12h 内 json_list 失败 14 个）。恢复需 `per_day=150`，涉及扩大收费预算，
要用户点头。

**待观察**：今晚（北京 01–03 点）会不会再次吃满额度。闸门生效后历史每天上限 120 篇
（≈600 次调用，占 9000 的 6.7%），理论上不会，但必须实跑一夜才能确认。

## 「页面最新一条为什么是几小时前」——排查口径（01:05 复核）

用户问「现在网站显示最新的新闻应该是」。结论：**不是故障，是排序键的必然结果**。

排查四步（下次直接照做）：
1. 抓 `/api/site/pool` 看 `items[0]`（页面 `all.tsx` 就是它，`headers()` 只有 `s-maxage=60`，
   本地 curl 绕过外网缓存即可，不必怀疑 CDN）。
2. 排序键在 `publication/pool.ts`：`display_at = coalesce(p.published_at, p.timeline_at)`
   ——**按原文发布时间排**。所以「刚收录的稿不显示在最上面」是设计使然（防搜索源回看 7 天
   的老稿占首页），只要那条稿有 `published_at`，它就落在原文那天。
3. 过滤是 `listedCondition` = `visibility='public' AND (NOT selected OR visible_after <= now)`，
   再加 **`p.eligible`**。`eligible` 与 `selected` 数量几乎相等（10-23: 720/710、10-24: 443/443），
   即「合格 ≈ 入选」；未入选的 pass 稿 `eligible=false`，**不进 pool**（只在详情页可见）。
   查「为什么这条不上页面」先看 `eligible`，不要先看 `visibility`。
4. `visible_after` 是入选稿的**延迟放行闸门**（本批 22:47 收录的三条放行时间 00:55）。
   放行状态一条 SQL 看清：`count(*) FILTER (WHERE visible_after <= now())` vs `> now()`。

本例实况：顶部是 10-24 08:41 收录的「西藏自治区将自然灾害救助应急响应提升至二级」
（`published_at` 为 null，故按收录时间落位、标签显示「收录」）。之后停摆 16 小时 →
恢复后处理的以历史稿为主（原文 10-23 及更早，落回旧分组）→ 22:47 至今新收 12 篇
全部 `eligible=false`（山西省委常委简历、云南人事观察、亚残运会闭幕，确属不对口）。

## 用户充值后：重跑 151 篇 failed（02:00）

**重跑方法（可复用）**：`failed` 是终态不自愈，捞回来的方式是直接改状态——
```sql
UPDATE articles SET processing_state='new', processing_error=NULL,
       processing_retry_at=NULL, processing_queued_at=NULL, processing_attempts=0
WHERE processing_state='failed';
```
**四个字段必须一起清**：`sweepUnprocessed` 的 WHERE 是
`state='new' AND (retry_at IS NULL OR <= now()) AND (queued_at IS NULL OR < now()-QUEUED_STALE)`，
只改 state 不清后两个，稿子永远不会被捞。改前先备份 id 列表（`/opt/yihot/backups/failed-ids-2026-10-25.txt`）。

**结果**：151 篇 → 已出版 128、**入选 22**（平均分 32.1），全部 `visible_after <= now()` 已放行。
首页顶部随之更新（沧州星月社 55 分、澎湃记者手记 58 分等上首页）。当日新闻队列清空。

**余额疑点（未解决）**：充完后查 `GET {LLM_BASE_URL}/user/balance`，
`is_available=true` 但 `total_balance` 仍只有 **8.63** 且在单调下降（9.98→9.15→8.64→8.63）。
402 确实消失了（近 20 分钟 296 次调用全 ok），但余额没涨 → **疑似充值未到账或充到别的账户**。
下次遇到「说充值了但余额没变」先让用户报充值金额与账户，别默认已到账。
按 1121 次/小时（≈¥1.5/h）的凌晨速度，8.63 只够 5–6 小时。

**另一个观察**：`llm_1h` 冲到 1121（per_hour 上限 1200）——重跑这种批量动作会贴着小时护栏跑，
剩下的历史稿因此排了 `processing_retry_at`。批量重跑要看一眼小时额度，别以为日额度有余就没事。

## 「为什么每次新源要回采」：两类老稿的实测画像（02:25）

用户想不通首采为什么要回补。查库后澄清——**代码里两个"老稿"标记不是一回事**：

1. **`first-import`（2694 篇 / 177 源，每个源一辈子只有一次）**：只在 `initialized_at` 为空那轮
   生效。**实测 88% 落在 30 天内（3-7 天 917 + 1-3 天 836 + 1-4 周 433 + <1 天 159），
   3 个月以外只有 114 篇，>1 年只有 9 篇。** → `initialBackfillMonths=12` 这道窗**几乎空转**，
   真正的闸门是条数（web_list 均 8.3 条/源、search 24.7 条/源），天花板是列表页深度。
   入池率 **35.5%**，反而高于常规增量稿（none，23.6%）——列表最上面几条是编辑手选的要闻，不差。
   名不副实：我们并没有真的"回采历史"，只是"新源第一次允许收 8 条而不限当天"。
2. **`stale-on-discovery`（2156 篇，每次采集都在发生）**：原文距今 >48h 就标记，
   **不受 `initialBackfillLimit` 管**。search 1490 篇（均龄 **4 天**，lookback=7 必触发，
   72 个搜索源无一 ≤3）；web_list 533 篇（**均龄 187 天**，归档页/侧栏漏入）；
   rss 89 篇（**均龄 1478 天**，etag 丢失后整份重读）。入池率 25.3%。
   → **持续花钱 + 让老稿显示成"今天"的其实是这一类**，降 `lookbackDays` 才是有效旋钮。

结论给到用户：`initialBackfillMonths` 12→1 是零风险改动（几乎不影响任何稿）；
`lookbackDays` **不能动**，见下节。

## 「每天只补近一周能省钱吗」：能省 ¥0.5/天，但会砍掉高入池率栏目（11:30）

用户问把回补限制在近一周。三种理解，逐个数：

1. **首采窗 12 月 → 7 天**：省 **≈¥0**。首采一辈子一次，84% 本就在 30 天内，
   天花板是列表 8 条，砍时间窗碰不到任何东西。
2. **增量年龄闸门 `ingestMaxAgeDays` 365 → 7**：能砍近一周入库的"非首采且老于 7 天"约 860 篇
   ≈ **¥0.5/天（¥15/月）**。代价具体且不轻：`rss-who-news` 73 篇（31 入池，**43% 入池率**）、
   福建省民政厅·通知公告 52 篇（19 入池）、广西民政厅两栏 44 篇（16 入池）——**慢更/存量型栏目
   会被整源断流**，而入池率都高于全站平均（26%）。**不划算，不改。**
3. **搜索 `lookbackDays` 7 → 3**：**上一轮我建议过，实测是错的**。3–7 天段恰是搜索源入池主力：
   近 7 天 3636 篇、927 入池；剔除首采后仍 1791 篇、292 入池（≈42 篇/天）。
   **省钱与保持入池量在搜索源上是对立的**，不能动。

**近 7 天成本真相（¥42.37）**：新稿 ¥9.82 + 搜索 ¥7.19 + **回填 ¥28.35**。
回填集中在 10-23（¥12.18）与 10-24（¥5.81）——正是集中加源那两天，**一次性**。
稳态下不加源就没有这笔钱。单篇均价：新稿 ¥0.0026 / 回填 ¥0.0039。

真正可动的三件事（按性价比）：① 不再集中大批加源（31 省已齐，最大一笔已过去）；
② 停掉"无日期条目"放行的泄漏——近 30 天 147 篇（2.2%）早于 12 个月、最老 2018-05，
39 篇已入池，要动的是**具体那几个源**不是全局窗口；③ `initialBackfillMonths` 12→1（零风险）。
