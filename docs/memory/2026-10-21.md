## 15:40 公众号三个大号解卡 + 正文解析 bug 修复

- **溯源 503 真因**：不是并发，是 EveryInfra 自己的容量耗尽。响应体
  `{"error":{"code":"unavailable","reason":"capacity_exhausted","message":"... wechat_oa/account_articles
  has no capacity right now and this call was refunded. Retry after 900s."}}`，`charged:false`
  （不计费），且 provider 自己已内部重试 1 次（`max_retries:1`）。
  之前误判为并发，靠「错峰」重试只是碰运气；单发探针 27s 后同样 503 即证明。
- **真 bug（正文取空）**：`everyInfraWechatArticle` 只读 `content_text`，而
  `article_detail` 实际只返回 `content_html`。公众号正文是排版 HTML，
  中国乡村发展基金会那批一律取空 → 分析无依据 → `relevance=unknown`。
  修复在 `providers/everyinfra.ts`：优先 `content_text`，退化用**保留段落换行**的
  剥标签兜底（不用 `lib/text.ts` 的 `stripTags`，它会把全文压成一行）；
  另把 `digest` 落进 `excerpt`，让「标题+摘要」也能分析。
  实测：青基会 16/16 pass；cfrf 4 篇纯图片贴（content_html 里 14 个 `<img>`、0 文字）
  用 digest 兜底，2 篇连 digest 都没有则标 `body_status='none'` 按标题判定。
- **调度退避改进**：`ProviderRejectedError` 增加 `retryAfterSeconds`；
  `collectSource` 失败分支区分「provider 说什么时候可以再来」——
  不计 `fail_count`、不降级健康，按 `GREATEST(retry_after, 900)` 秒回来重试。
  否则 60 分钟间隔的源会被 `interval*(fail_count+2)` 推到 4~6 小时后，错过容量窗口。
- **构建加速**：给 Dockerfile 加 `ARG APT_MIRROR`、compose 加 `args: APT_MIRROR/NPM_REGISTRY`
  （默认空=上游，不影响他人）；服务器 `.env` 设 aliyun + npmmirror 后，
  `docker compose ... up -d --build` 从 20+ 分钟降到 **3 分 53 秒**。
  卡点主要是 Debian 源和 npm 上游源，不是 CPU。

## 追加：还有第五道门 —— 列表页会把精度覆盖回去（这才是「反复收不了」的真根因）

上一条记录的四层是"静态"原因；实际修完后**一小时就复发**。

`upsertMaterial`（content/materials.ts）：已存在的文章，只要新回报的 `publishedAt` 与库里的不同
就 UPDATE。而列表页**每次采集都回报** `00:00 + precision='date'`，它与已升级的 `17:45` 不相等
→ 触发 UPDATE → `published_at` 写回 00:00、`published_at_precision` 写回 `date`。

实测：19:00 回填 74 篇 datetime → 19:05 跑一次 collect → 列表页那 20 条**全部退回 date**
（另外 54 条已离开列表页没被动，看起来"大部分是好的"，极容易误判为修好了）。

**修法**：加「精度不降级」
```ts
const downgrade = existing.published_at_precision === "datetime" &&
  (m.publishedAtPrecision ?? existing.published_at_precision) === "date";
if (!downgrade && corrected.publishedAt && ...) { /* UPDATE */ }
```
更细的 claim 仍可修正列表页（详情页能改），只是反向被拦。

**验证纪律（重要的方法论）**：只回填不跑采集，看到的 datetime 是假象。
必须 回填 → 跑 `collect.ts <sourceId>` → 再查 precision，两次都是 datetime 才算修好。

## DeepSeek 开放了 Search / Fetch API —— 这条路比热榜好得多（已实测）

用户问「聚合新闻热榜有多少、他们不开 API，deepseek 有没有专门搜索 API」。

### 热榜生态现状

- 官方有热榜的平台约 30 个（微博/抖音/快手/小红书/知乎/B站/头条/百度/腾讯新闻/网易/搜狐/
  澎湃/虎扑/豆瓣/贴吧/V2EX/36氪/IT之家/少数派/财联社/华尔街见闻/雪球/东财/同花顺/GitHub…），
  **基本都不开公开 API**（微博开放平台需企业认证且不给热搜榜原样数据）。
- 有 API 的**全是第三方反向工程聚合器**：tophub.today（号称 300+ 节点，实测 /c/news 为 12 榜 420 条）、
  NewsNow（开源，52 源，有公开 API + MCP server，缓存 30min）、DailyHotApi（imsyy，≈50 平台，输出 JSON/RSS，可自建）、
  Hot Search API（Go，31 源）、tkme.cn（付费 ¥0.01/次）、新榜/蝉妈妈/飞瓜（SaaS 付费）。
- 结论：热榜这条路的本质缺陷不是「有没有 API」，而是**它拿不到发布时间、链接常被替换成搜索页**
  （见上面 tophub 实测：291/420 = 69% 是搜索结果页）。

### DeepSeek Search / Fetch API（2026-10-17 上线）

- `POST https://api.deepseek.com/v1/tools/search` / `.../tools/fetch`
- 计费 **¥5/1000 次成功请求 = ¥0.005/次**；只有 200 且结果非空才计费；`count` 不影响价格
- QPS：Search 100 / Fetch 25（账号级）
- 搜索语法：`site:` `-site:` `-词` `"短语"` `lang:zh` **`after:2026-10-14`** **`before:`**
- 返回：`rerank_score`(0–3, ≥1.5 优质) / `title` / `url` / `snippet` / `summary`(600–800字) /
  `content`(需 need_content) / `site_name` / `date`(UTC RFC3339) / `authority`(0–4, ≥3 极权威)
- 项目直连 `api.deepseek.com/v1`，**同一个 LLM_API_KEY 直接可用**

### 实测（用项目 key，8 组儿童权益查询 × count=20，after:2026-10-14）

| 指标 | 结果 |
|---|---|
| 原始 / 去重 | 160 / **149** |
| **库里没有的** | **148 / 149**（现有 118 个源只覆盖 1 条）|
| authority ≥3 | 136 条（91%）|
| 时间精度 | **149 条全部 00:00（北京时间）→ 只到日** |

| Fetch 正文 | 干净 markdown，846 字，标题正确 |

来源质量很高：民政部通知、检察院未保案例、法院判决、国务院妇儿工委办、地方政法委——正是
现有源结构上拿不到的**一手垂类**。

**关键坑**：`date` 只到日（00:00），接进来会直接落进刚修好的「precision='date' 不显示钟点」。
要钟点必须再走一次详情页/Fetch（Fetch 另收 ¥0.005/次）。这是设计时必须先定的取舍。

### 成本模型

- Search：8 查询/天 × ¥0.005 = ¥0.04/天 ≈ **¥1.2/月**
- 分析：新增 60–100 篇/天 × ¥0.0035 ≈ ¥0.2–0.35/天 ≈ **¥6–10/月**
- 合计 **¥8–12/月**（当前 LLM ¥25–35/月，约 +30~40%）

### 接入的工程量

现有 kind 只有 `web_list`(40) / `json_list`(17) / `rss`(8)，**没有 search**。需新增
`kind: "search"` 的采集器（照 `rss.ts` 的 candidates 模式，约 60 行），config 放 queries[]、
after 天数、count、authority 下限。主题过滤可以省掉——**查询本身就是议题，这才是它胜过热榜的根本原因**。
