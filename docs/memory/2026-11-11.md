## 数据库归档（新增能力）
- 用户问「归档是不是下载到本地再清空云端、能不能一年一归档」。查库：数据从 2026-09-30 起共 **42 天**，总量 1.29GB（receipts 417MB/105,943 行、articles 362MB/29,625 行、article_revisions 100MB/46,320 行）。**现在按任何保留期都删不到东西**，年度归档要等 2027-01 才有第一个完整年；按 30MB/天增速一年约 11GB，25GB 空闲只够两年。
- 新建 `scripts/archive-db.py`：`COPY (SELECT … WHERE ts < cutoff) TO STDOUT WITH CSV HEADER` → gzip 到 `/opt/yihot-archive/<年>/`，文件名带首末行时间（北京时区），`manifest.json` 记行数/字节/sha256/截止时间。删除用 **ctid 分批 5000**（`article_revisions` 是 (article_id, revision) 复合键，按 revision 删会误伤别的文章）。规则：导出行数 ≠ 应删行数就中止；删完复查过期行必须为 0。
- 保留期：receipts/attempts/revisions 180d、fetch_runs 90d、hot_rankings 365d；**articles/publications/analyses/reports 永不删**。
- 踩坑：`psql -tAc "DELETE … RETURNING 1"` 会把 `DELETE 12003` 这条命令标签也打到 stdout，计数多 3 行导致断言失败 → 加 `-q` 且只数等于 `1` 的行。
- 实测：导出 fetch_runs 30d = 3531 行 / 67KB，CSV 头正常；临时表 12,000 行删除路径 `before=12000 removed=12000 after=0` 通过，探针表已 DROP。
- 宿主 root cron 加 `40 4 1 * * /usr/bin/python3 /opt/yihot/scripts/archive-db.py`（**只导出，不带 --delete**）；`MAINTENANCE.md` 新增「数据库归档」一节。

## 选 A：高频源抓取间隔降到 10 分钟（12:43–13:00）

- 起因：上一轮问「午间空窗怎么办」给了 A/B/C 三选项，用户选 A（缩短 thepaper / caixin 的抓取间隔）。
- **关键前提**：sources.interval_minutes 不是配置项，是 adaptIntervals() 每天 04:20 按近 7 天日均产出重算的结果。直接 UPDATE 表只在当天有效，明天 04:20 会被公式盖回来——所以必须改公式，不能只改数据。
- 旧公式 24*60/(perDay*3) + min=15 的问题：thepaper 日均 81.9 篇算出 5.9 → 被 min 卡到 15（比它自己的产出节奏还慢）；chinanews-scroll 35.7 → 13.4 → 也被卡到 15；caixin 23.1 → 20.7，但表里写 20，说明旧值是人手改的、且压不过公式。
- 改法（packages/backend/src/sources/collect.ts）：min 15→10；新增 samples = perDay>=20 ? 6 : 3。按真实数据模拟，只有 3 家变（thepaper 15→10、chinanews-scroll 15→10、caixin 20→10），其余 60 个源一个不动。
- 部署：build api（1m47s）→ recreate api + worker，两个容器 Image 都是 aihot-app:latest。web 没动（3 天前镜像，本次无前端改动）。
- 立即生效：UPDATE sources SET interval_minutes=10, next_fetch_at=now() WHERE id IN (三家)（UPDATE 3）。调度器 sources.schedule 是 * * * * *，每分钟一次，10 分钟间隔跑得准。
- 提交 bc88813（代码）+ 8e89bbd（手册新增「信源抓取节奏：adaptIntervals」一节）；远端最新 5a9c68f（含 CI 自动刷新的 PDF）。服务器 0 diff（768 文件）。
- **成本**：只增抓取流量，不增分析——同一篇稿子无论列表被读几次，articles 里只有一行。fetch_runs 约 +168 行/天，90 天归档无压力。
- **老实说**：抓取变快解决不了午间空窗。源本身不发稿的时段还是空的，这一项只是把发现延迟从 15–20 分钟压到 10 分钟内。
